# SovaGrid

SovaGrid — набор отдельных приложений и служб для доступа к серверам, наблюдения за их состоянием и реагирования на события.

После 1.0.0 в исходниках готовится допуск по [зависимостям и возможностям системы](SYSTEM_REQUIREMENTS.md), без белого списка названий и версий дистрибутивов. Опубликованные пакеты 1.0.0 пока сохраняют прежние ограничения Ubuntu.

## Репозитории

| Репозиторий | Назначение |
|---|---|
| [sovagrid-hub](https://github.com/sovagrid/sovagrid-hub) | API, пользователи, роли, история метрик, инциденты, Telegram и очередь заданий |
| [sovagrid-agent](https://github.com/sovagrid/sovagrid-agent) | Сбор метрик и исполнение явно разрешённых заданий на Ubuntu |
| [sovagrid-apple](https://github.com/sovagrid/sovagrid-apple) | Нативные приложения для iPhone, iPad и macOS |
| [sovagrid-android](https://github.com/sovagrid/sovagrid-android) | Нативное приложение для Android |
| [sovagrid-web](https://github.com/sovagrid/sovagrid-web) | Веб-панель для компьютера и мобильного браузера |
| [sovagrid-connect](https://github.com/sovagrid/sovagrid-connect) | Настольный запуск полной веб-панели через SSH для macOS, Linux и Windows, включая ProxyJump |
| [sovagrid-vpn](https://github.com/sovagrid/sovagrid-vpn) | Раздельный сбор состояния Amnezia и собственного WireGuard без доступа Hub к Docker socket; root-only CLI для WireGuard |
| [sovagrid-blueprint](https://github.com/sovagrid/sovagrid-blueprint) | Установщик, архитектура, модель доступа и план развития |
| [sovagrid-update-feed](https://github.com/sovagrid/sovagrid-update-feed) | Подписанная лента серверных релизов; подписка включается отдельно на поддерживаемой установке Hub |

Девять репозиториев находятся в [организации sovagrid](https://github.com/sovagrid). Новые исходники открыты по MIT; опубликованные ранее пакеты сохраняют тексты лицензий своего выпуска.

Текущий серверный выпуск — [SovaGrid 1.2.1](https://github.com/sovagrid/sovagrid-blueprint/releases/tag/server-v1.2.1). Он включает установку Agent через несколько SSH-переходов и исправление проверки подписанного обновления после загрузки сервера. [Быстрый запуск](QUICKSTART.md) содержит команду для пустого сервера. Точные версии пяти компонентов закреплены в манифесте архива. [Контрольные суммы](https://github.com/sovagrid/sovagrid-blueprint/releases/download/server-v1.2.1/SHA256SUMS).

[Подписанная лента](RELEASE_FEED.md) позволяет отдельно включить серверные обновления в Web или Connect; по умолчанию подписка выключена. Уже установленные `v0.13.0` и `v0.14.0` требуют разового ручного перехода через Connect: [проверка для `v0.13.0`](https://github.com/sovagrid/sovagrid-connect/actions/runs/41227574940) и [для `v0.14.0`](https://github.com/sovagrid/sovagrid-connect/actions/runs/41227133745) подтвердила переход на `v0.14.1`, откат при намеренном сбое и сохранение Web Agent. Отдельный [прогон опубликованной полной 0.14.1](https://github.com/sovagrid/sovagrid-blueprint/actions/runs/41298983265) подтвердил её установленный подписанный updater: отказ при повреждённой подписи, ожидание простоя, применение кандидата и откат при намеренном сбое. [Hub-only 0.14.1](https://github.com/sovagrid/sovagrid-blueprint/actions/runs/41298989964) сначала проходит ручной переход на новый согласованный пакет, после чего поддерживает подписанное обновление с сохранением внешнего Agent и SSH-транспортов.

Пять серверных репозиториев можно собрать в [переносимый пакет](package_server.py) без локальных секретов и Git-метаданных. На новом Ubuntu-сервере [SovaGrid Connect](https://github.com/sovagrid/sovagrid-connect) принимает этот пакет через графическое окно, проверяет его, передаёт по SSH и запускает установку. На уже установленном сервере Connect может включить WireGuard, терминал, файловый раздел и чтение журналов выбранных systemd-служб через отдельное подтверждённое действие после проверки исходников и служб. Для журналов устанавливается отдельный непривилегированный broker с собственным перечнем точных имён `.service`; пользователь Agent не входит в группу `systemd-journal`. Доступ к приватному GitHub и ввод токена на сервере не требуются. SSH-пароли, первый пароль Hub, пороги мониторинга и токен BotFather вводятся или копируются в интерфейсе. Создание пакета из исходников остаётся задачей сборки; готовый пакет можно передать пользователю вместе с приложением.

Для резервной копии всего управляемого состояния хоста есть [root-only backend и контракт Connect](HOST_BACKUP.md). Он архивирует секреты отдельно от снимков базы Hub. Подтверждённый запрос через Connect ведётся независимым systemd worker: он временно останавливает только локальные writer-службы, создаёт копию с заранее закреплённым ID и восстанавливает исходные состояния даже после обрыва SSH. Глобальный администратор может создать переносимую копию в Web, проверить её и скачать все пять файлов отдельными одноразовыми загрузками: архив хоста, его манифест, Docker-образы, их манифест и квитанцию. Web и Connect доставляют на чистую Ubuntu независимо закреплённый исполнитель, передают пять файлов, показывают подтверждаемый план и находят сохранённую операцию после обрыва. Транзакция применения, карантин старых команд, проверка здоровья, откат и восстановление реализованы; запуск зависит от capability проверенного исполнителя и готовности цели. Применение full/v2 включено в проверенном исполнителе 1.0.0; ограничения описаны в [контракте резервной копии](HOST_BACKUP.md) и [составе выпуска](RELEASE_1_0.md). Наличие мастера не добавляет эту capability старому серверному архиву.

## Первые сценарии

1. Пользователь добавляет SSH-профиль и выполняет команды в мобильном приложении. Профиль поддерживает вход по паролю или ключу, а ключ хоста проверяется до отправки учётных данных. Для сервера за промежуточным SSH-хостом можно указать отдельные учётные данные и ключи обоих узлов.
2. Администратор добавляет сервер через SSH-мастер Connect или Web. Мастер проверяет ключи, показывает план и после подтверждения сам готовит Agent, токен и постоянный транспорт к выбранному Hub. Учётные данные общей службы SovaGrid не нужны.
3. С телефона пользователь открывает веб-панель через временный SSH-проброс к выбранному серверу с Hub; при необходимости маршрут проходит через промежуточный SSH-хост. На компьютере то же делает SovaGrid Connect. Начальный пароль можно скопировать в этих приложениях после SSH-входа без чтения файла в консоли. Панель показывает метрики, историю, последние десять процессов по памяти, инциденты, окна обслуживания, журнал, очередь команд, подробное состояние Amnezia и собственные WireGuard-инстансы SovaGrid. Системная, светлая и тёмная темы выбираются на каждом устройстве отдельно. Процессы передаются без аргументов команд и не записываются в историческую базу. В «Настройках» администратор меняет пароль и пороги тревог без перезапуска. Ошибка одного источника не скрывает состояние другого.
4. Администратор может запустить разовую команду или несколько независимых вкладок интерактивного терминала из панели при включённой функции на сервере и в Agent. Терминал работает от пользователя `sovagrid-shell` без доступа к токену Agent; его байты не попадают в аудит. Файловый раздел позволяет читать и править небольшие текстовые файлы, загружать двоичные файлы до 4 МБ и скачивать до 32 МБ только в разрешённых на Agent каталогах. Журналы systemd читаются только для явно разрешённых служб после отдельного включения; их просмотр требует разрешённых удалённых команд в Hub и Agent. В разделе Telegram администратор вставляет токен BotFather, а пользователь отправляет боту `/start`; заявка появляется в панели, где администратор подтверждает роль `viewer`, `operator` или `admin`. Привязанные пользователи могут запросить сводку VPN через `/vpn`; Telegram-команда на сервере дополнительно требует роль `admin` и подтверждение.
5. При необходимости администратор отдельно включает стандартный WireGuard: `run.sh --with-wireguard` готовит зависимости и локальный root broker. В панели администратор выбирает сервер с Agent и после подтверждения может подготовить инстанс, запустить его, добавить или отозвать клиента, скачать клиентский профиль `.conf` или удалить инстанс. При скачивании браузер создаёт временную пару ключей; брокер шифрует профиль до передачи Agent и Hub. Нативные приложения предлагают системное сохранение после расшифровки в веб-панели. Закрытый ключ профиля не попадает в базу Hub. Выбранный Agent отправляет собственную очищенную VPN-сводку примерно раз в 30 секунд; панель показывает её свежесть отдельно от состояния VPN на хосте Hub. Панель содержит отдельный SSH-мастер подготовки VPN-кода и брокеров, включая поддерживаемые установки AmneziaWG. Каждая изменяющая операция требует плана и подтверждения; обычный `run.sh` существующую Amnezia не меняет. Автоматическая установка AmneziaWG поддерживает amd64; новая полная Web-проверка этого пути отдельно не заявляется.

В установленной веб-панели администратор может открыть «Добавить сервер → Подключить по SSH» и запустить терминал ещё до установки Agent на целевой сервер. В поле цели укажите IP или DNS-имя машины, на которую хотите войти, и её SSH-порт. Если цель видна только с другого сервера, добавьте его как переход и укажите его собственные SSH-реквизиты. Мастер поддерживает цепочку до 16 переходов для терминала, проверки состояния и установки Agent с совместимым брокером.

Для установки нажмите «Проверить состояние», затем «Проверить связь и подготовить установку». Целевой сервер должен видеть SSH-порт Hub. После подготовки сверяйте путь в плане и отдельно подтверждайте запуск Agent. Для восстановления выбирайте незавершённую запись и заново вводите тот же маршрут и SSH-реквизиты.

Для домашнего сервера с готовым обратным туннелем `-R 2222:localhost:22` переходом будет VPS с его обычным SSH-портом, а целью — `127.0.0.1:2222` со стороны VPS. Реквизиты цели принадлежат домашнему серверу. Сверьте отпечаток каждого узла при проверке маршрута. Обновление исходного внешнего Agent на сервере с собственным Hub доступно отдельно в «Настройки → Обновление внешнего Agent» после подготовки пакета через Connect и просмотра точного плана.

Текущая реализация и ограничения каждого приложения описаны в README соответствующего репозитория. План дальнейшей разработки: [ROADMAP.md](ROADMAP.md).

Быстрый запуск на Ubuntu: [QUICKSTART.md](QUICKSTART.md). Полная инструкция по [run.sh](run.sh), секретам и проверкам: [DEPLOY.md](DEPLOY.md).

## Подробные графики с Prometheus

Начиная с SovaGrid 1.2.1 администратор со всеми правами на Hub может установить Prometheus из панели. Откройте «Настроить Prometheus» на экране «Начало работы» или в разделе «Настройки → Подробный мониторинг». Установку можно начать сразу после входа в Hub.

1. Нажмите «Развернуть Prometheus» и подтвердите установку на хосте Hub. Мастер покажет, когда сбор метрик начнётся.
2. Когда в Hub появится хотя бы один сервер, выберите его. В списке источников выберите «Prometheus SovaGrid», нажмите «Проверить источник», затем «Подключить источник». Привязка сохраняется для выбранного сервера.
3. Откройте «Обзор → Подробные графики». Пользователи увидят CPU, память и диск доступных им серверов.

Prometheus запускается в отдельном проекте Docker Compose и слушает внутренний адрес Hub. Панель сама передаёт измерения, поэтому отдельные Prometheus на управляемых серверах не нужны. Графики заполняются по мере поступления новых измерений. При переносе Hub разверните сборщик на новом хосте из мастера. Хранилище истории Prometheus ведётся отдельно от резервной копии Hub.

Из проверенного установленного пакета тот же сборщик запускается командой `sudo /opt/sovagrid-src/sovagrid-blueprint/run.sh --with-prometheus`.

Для подключения уже работающего Prometheus при отдельном запуске Hub владелец передаёт доверенный каталог через `serve --detailed-monitoring-sources-file`. Источник должен отдавать ряды `sovagrid_cpu_percent`, `sovagrid_memory_percent` или `sovagrid_disk_percent` с меткой `server_id`. Администратор панели выбирает источник в мастере, указывает значение этой метки и проверяет связь. [Контракт и схема установки](deploy/MANAGED_PROMETHEUS_CONTRACT.md).

## Удалённый Agent

Новый Agent-only protocol для Connect описан в [REMOTE_AGENT.md](REMOTE_AGENT.md): постоянное подключение другого Ubuntu через существующий SSH endpoint Hub, подготовка token и ключа на target, безопасный повтор и ограниченный отзыв доступа. После установки Hub тот же сценарий доступен в веб-панели через мастер «Добавить сервер → Подключить по SSH»: он сверяет ключ целевого сервера, проверяет состояние, показывает подготовленную установку и требует отдельного подтверждения запуска. [Требования и порядок](DEPLOY.md#добавление-другого-ubuntu-сервера-из-веб-панели) описаны в инструкции. Для этого сценария Hub сначала обновляется обычным способом до версии с enrollment API и проверенным helper; старый установленный Hub не изменяется по неподтверждённому сценарию.

Разрешения команд, терминала и файлов отдельного Agent меняются через [SSH-мастер панели](deploy/WEB_AGENT_FEATURES.md): проверка текущего состояния, план и отдельное подтверждение. Мастер проверяет новые метрики и завершает очистку до открытия политики Hub. Пароли и приватные ключи используются только для текущего запроса.

Журнал root helper ограничен 4 МиБ на узел. На Hub сохраняются до 2048 enrollment-записей, включая отозванные, и до 256 неотозванных разрешений туннеля, включая незавершённые установки. При достижении лимита новая авторизация отказывается без изменения ресурсов; проверка, отзыв и точный повтор существующей авторизации остаются доступны. JSON-запросы и ответы helper по-прежнему ограничены 32 КиБ.
