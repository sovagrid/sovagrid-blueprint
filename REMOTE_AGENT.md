# Удалённый Agent через Connect

Agent-only сценарий использует отдельный [helper protocol 1](deploy/remote_agent.py) и текущий вход администратора Hub в Connect. Обычный `run.sh` продолжает устанавливать полный серверный набор. Root helper поддерживает Ubuntu 22.04, 24.04 и 26.04 с Python 3.10+, systemd 247+ и OpenSSH; SSH-пользователь должен быть root либо иметь доступный без запроса пароля `sudo -n`.

Connect сначала выполняет проверку без изменений и показывает состав установки. На целевом сервере устанавливаются Agent для метрик и сетевых проверок, отдельная служба SSH-туннеля и необходимые пакеты Ubuntu. Команды, интерактивный терминал, файлы, systemd-журнал и VPN при этом выключены. Существующий Agent, чужой unit, пользователь или управляемый путь вызывают отказ вместо автоматической замены.

На целевом сервере создаются случайный Agent token и независимая пара Ed25519 для туннеля. Во время установки Connect получает только token SHA-256, открытый ключ и постоянные идентификаторы. В обычном runtime Agent передаёт bearer Hub через проверенный HTTPS. SSH private key остаётся root-only на target, а служба отдельного UID получает временную копию через systemd LoadCredential. Agent UID не получает доступ к этой копии.

## Постоянное соединение

```text
Agent → https://localhost:18767 → SSH tunnel на Agent
      → существующий SSH endpoint Hub → 127.0.0.1:8767 → Hub API
```

На target появляется только loopback listener. Новый публичный порт Hub не открывается. Обратный туннель целевого сервера не создаётся и не изменяется: постоянный маршрут Agent → Hub проверяется с самого Agent. Локальный ProxyJump-профиль компьютера служит для установки, но не копирует его приватные ключи на сервер.

На Hub создаётся отдельный UID на Agent с одной ограниченной строкой публичного ключа. Разрешено только TCP-назначение `127.0.0.1:8767`; shell, exec, SFTP, PTY, `-R`, Unix sockets, SSH-agent и X11 запрещены. OpenSSH использует один тип канала для `-L` и `-D`, поэтому проверка ограничивает назначения SOCKS, а не обещает запрет самого синтаксиса `-D`. Hub также не управляет адресом локального listener у держателя ключа. [OpenSSH sshd_config](https://man.openbsd.org/sshd_config), [authorized_keys](https://man.openbsd.org/sshd).

В первом инкременте совместимы существующие блоки `Match User`, `Match Group` и `Match all`. Условия по адресу, hostname, local port и другим контекстам требуют отдельного согласования: helper отказывает, поскольку проверка одного `sshd -T -C` не доказывает ограничения для всех возможных соединений. Существующие AllowUsers/AllowGroups и запреты не расширяются автоматически.

Hub SSH host key и публичный CA читаются через уже проверенное SSH-соединение. CA-файл должен содержать только PEM certificates; комбинированный файл с приватным ключом отвергается. В HTTPS сохраняется имя `localhost`, соответствующее сертификату Hub. `ExitOnForwardFailure` проверяет создание listener; готовность дополнительно требует TLS-проверенного `/healthz` и первого принятого образца метрик. [OpenSSH client options](https://man.openbsd.org/ssh_config).

## Повтор и отмена

Четыре сохраняемые фазы: `prepared → transport_ready → registered → active`. Target хранит root-owned журнал, Connect — только публичные данные возобновления. Повтор одного request UUID возвращает те же идентификаторы, token digest и SSH public key. Потеря ответа регистрации не создаёт второй сервер: Hub идемпотентно принимает тот же enrollment ID и digest.

Перед изменением сверяются bundle manifest, функции установки, SSH policy, хеши и метаданные собственных файлов/каталогов/UID. Изменения администратора приводят к новому preview или отказу. Неполная либо повреждённая пара секретов не заменяется новой незаметно.

Внутренний root-owned журнал на каждом узле ограничен 4 МиБ; лимит публичного JSON-запроса и ответа остаётся 32 КиБ. На Hub допускаются 2048 enrollment-записей суммарно, включая отозванные tombstones, и 256 неотозванных разрешений туннеля, включая начатые установки. Превышение любого лимита при новой авторизации возвращает `STATE_CONFLICT` до записи журнала и изменения ресурсов. Проверка, отзыв и точный повтор уже существующей авторизации работают при достигнутом лимите; отзыв освобождает место среди неотозванных разрешений, но сохраняет tombstone в общем журнале.

Отмена после регистрации сначала должна отменить pending запись Hub. Если Agent уже успел передать метрики, отмена не удаляет работающую установку. Cleanup останавливает только собственные службы, удаляет только проверенные ресурсы и на Hub завершает действующие sshd-процессы только своего UID с проверкой PID/UID/start-time. Удаления строки ключа недостаточно для отзыва уже открытого туннеля. Неоднозначное частичное состояние возвращает `CLEANUP_REQUIRED`; полный откат не заявляется.

## Функции подключённого Agent

В следующем мастере Connect 0.3.6 **«Функции другого сервера…»** доступны явное разрешение удалённых команд и дополнительные PTY/файлы `workspace`. PTY и файлы требуют разрешения команд в нынешнем runtime. Разовые команды администратора выполняются от Agent UID; PTY использует отдельный `sovagrid-shell` без групп Agent и без доступа к его токену. VPN и журналы этот мастер не включает.

Мастер принимает новый проверенный пакет независимо от старого enrollment-журнала. Установленные runtime, исходный helper, манифест первоначальной установки, IDs, token и ключ туннеля не заменяются. Runtime сверяется с разрешённым новым пакетом; несовпадение возвращает `AGENT_UPDATE_REQUIRED`. Дополнительные units и отдельный пользователь терминала принадлежат root-private sidecar `/var/lib/sovagrid-agent-enrollment/features.json`. Writable workspace и shell home проверяются отдельно по UID/GID/mode, не включаются в старый список root-owned каталогов и не удаляются при выключении функций.

Новые действия `target-features-status`, `target-features-preview`, `target-features-apply` исполняются только из полностью проверенного временного пакета. Старые actions и их ответы остаются совместимыми. Статус принимает `{protocol:1,server_id}`; preview добавляет `features:{commands,terminal,files}`; apply дополнительно требует `expected` с четырьмя CAS-хешами, `enrollment_id` и `agent_token_sha256`. Все флаги — строгие booleans; terminal/files без commands отклоняются. Статус и preview не меняют конфигурацию Agent. CAS охватывает источник, первоначальную установку, sidecar, собственные units, пользователей, метаданные каталогов и политику systemd.

Перед применением Connect сверяет целевой Agent с активной регистрацией Hub и закрывает общий gate управления через API с ревизией. Только после проверенной настройки Agent gate согласуется с выбранным разрешением команд. Перед сообщением об успехе мастер ждёт новое измерение, повторно проверяет target и ревизию Hub. Потерянный ответ или отмена не означают откат: сохранённое намерение и собственные временные пакеты сверяются при повторной проверке. Настройки SSH-маршрута и пользовательские файлы сохраняются.

PTY-пользователь имеет `/nonexistent` в passwd и создаётся с уже истёкшим сроком действия учётной записи. Рабочий каталог и `HOME` самого PTY остаются `/var/lib/sovagrid-shell`. Это не SSH-пользователь: одного `nologin` недостаточно для запрета входа только ради forwarding. Проверка доступа к токену выполняется после прямого сброса UID/GID без чтения его содержимого; парольные данные NSS не возвращаются и не записываются.

Writable-каталог сначала создаётся как отдельный root-private временный сосед. Sidecar сохраняет его устройство/inode перед публикацией с запретом замены назначения. Потерянный ответ допускает продолжение только для этого записанного inode. Чужое назначение не присваивается и не удаляется; до его явного разрешения операция остаётся незавершённой. При прерывании до сохранения inode может остаться пустой private-каталог `.sovagrid-feature-data.*`, который не присваивается автоматически.

## Проверки разработчика

```sh
python3 -m unittest discover -s tests -v
docker build -f tests/Dockerfile.sshd --build-arg UBUNTU_VERSION=24.04 -t sovagrid-ssh-fixture .
docker run --rm --init --network none sovagrid-ssh-fixture
```

Контейнерная проверка создаёт собственные UID, TLS fixture и настоящий sshd только внутри одноразового контейнера, без host mounts, опубликованных портов и privileged mode. Она проверяет разрешённый проброс, запрещённые каналы/назначения, условные policy-конфликты, идемпотентность и отзыв одного активного UID при сохранении другого и root-соединения. Это не заменяет проверку systemd LoadCredential/cgroups, reboot и восстановления реальной сети на отдельном Ubuntu-хосте.
