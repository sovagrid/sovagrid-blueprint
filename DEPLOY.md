# Развёртывание SovaGrid на Ubuntu

`run.sh` устанавливает Hub и веб-панель в отдельные непривилегированные Docker-контейнеры, а Agent — как непривилегированную службу systemd на Ubuntu. Agent работает на хосте: поэтому `/proc`, корневая файловая система и сетевые интерфейсы в его метриках относятся к серверу, а не к контейнеру. Скрипт рассчитан на один сервер и не меняет чужие Docker-проекты.

Сначала выберите доверенный набор исходников или проверенный серверный архив. Для каждого нового пакета проверяйте SHA-256, манифест и результат интеграционной установки на одноразовой Ubuntu. Архивы прежних preview-выпусков временно изъяты для удаления частных примеров; инструкции ниже не требуют доступа к какому-либо демонстрационному серверу.

Для **первой установки без терминала** откройте SovaGrid Connect на компьютере, укажите новый Ubuntu-сервер с root SSH-доступом, нажмите «Установить на сервер…» и выберите доверенный `SovaGrid-server-source.tar.gz`. В том же окне выберите WireGuard, терминал, файловый раздел и, при необходимости, журналы конкретных systemd-служб. Для журналов введите точные имена `.service` по одному в строке. Connect проверит структуру и SHA-256 каждого файла пакета, состояние сервера, покажет SSH-запросы в графических окнах и передаст пакет только после проверки. Затем он запустит этот `run.sh`. На уже управляемом сервере действие первой установки откажет до передачи архива; для подключения используйте обычную кнопку «Подключиться». Манифест защищает от повреждения архива, а происхождение пакета проверяйте по источнику его получения. Для входа нажмите «Получить начальный пароль по SSH» в Connect — читать `/etc/sovagrid/admin-password` в консоли не требуется.

Если на Ubuntu уже работает SovaGrid Agent, подключённый к другому Hub, используйте отдельный мастер Connect **«Свой Hub на сервере с Agent…»** с проверенным серверным пакетом. Он принимает проверенный `root` SSH или существующего пользователя с `sudo -n`, сохраняет внешний Agent и его туннель и добавляет отдельный локальный Hub с новым Agent. Гарантии и ограничения описаны в [PROMOTION.md](PROMOTION.md). Обновление такого Hub выполняется отдельным Hub-only путём; исходный внешний Agent можно обновлять только отдельным root CLI с review и live idle ACK по [EXTERNAL_AGENT_TRIAL.md](deploy/EXTERNAL_AGENT_TRIAL.md). Веб-мастер этой операции ещё не готов.

На сервере с собственным Hub и внешним Agent можно отдельно включить локальный PTY, рабочую папку второго Agent и инвентарь Docker. Локальный collector читает Docker от root и отдаёт второму Agent только очищенный снимок. Перед включением Connect показывает план и проверяет сохранность внешнего Agent и SSH-туннеля.

Для **включения функций на существующем сервере** используйте «Включить функции…» в Connect. Перед запуском Connect без записи проверяет root SSH, Ubuntu, владельцев и права исходников в `/opt/sovagrid-src`, маркеры установки, работающие Hub/Web и Agent. Он показывает текущие функции и разрешённые журнальные службы, требует подтверждение и повторяет проверку непосредственно перед запуском уже установленного `run.sh` с выбранными флагами. Выбранный список журналов **целиком заменяет** прежний; для сохранения службы укажите её снова. При ошибке он не запускает скрипт; если всё выбранное уже включено, изменений нет. Во время включения Hub/Web и Agent могут перезапуститься. Эта кнопка не загружает новые исходники и не настраивает Amnezia. Старый исходный код без journal broker будет отклонён до изменения сервера; один лишь подготовленный пакет обновления новую функцию не включает.

Для **графического обновления действующей версии** используйте «Обновить сервер…» в Connect. Подготовка проверяет SHA-256 архива и манифест, затем сохраняет кандидат отдельно в `/opt/sovagrid-candidates/<sha256>` без перезапуска служб. Кнопка «Применить обновление» требует ещё одного подтверждения. Перед изменением версии Connect сверяет манифест текущего `/opt/sovagrid-src` с тем, что был показан в диалоге, заново проверяет SHA-256 staged-архива и все извлечённые исходники, состояние Hub/Web/Agent и включённые функции. Затем под закрытым root-only путём сохраняет старые исходники и образы, конфигурацию, управляемые units, данные Hub/Caddy и инвентаризацию VPN; Hub и Web останавливаются на время снимка. Новый `run.sh` получает прежние флаги WireGuard, терминала, файлов и точный allowlist журнала. Отдельный брокер Amnezia этим действием не включается и не удаляется.

После установки проверяются Docker image ID и здоровье Hub/Web, HTTP/HTTPS, Agent, sockets/timers, версия и функции. Если проверка или установка провалилась, updater пытается восстановить старые исходники, образы, базу и службы. При прерывании следующая попытка сначала восстанавливает незаконченную операцию и требует повторного предпросмотра. Если восстановление не проходит, копия остаётся в `/opt/sovagrid-candidates/transactions/` и Connect явно сообщает о неполном откате. Это не атомарная системная транзакция: изменения APT и системных пользователей не удаляются, сторонний код может иметь внешние побочные действия, а записи в новую версию до провала поздней проверки могут быть потеряны. Одновременный ручной запуск `run.sh` не поддерживается. Для применения нужен исходный пакет с корректным манифестом у уже управляемой Ubuntu-установки; непроверенный Git checkout без манифеста отклоняется. Происхождение пакета SHA-256 не подтверждает.

### Автообновление на самом сервере

`run.sh` устанавливает `sovagrid-auto-update.timer`, но **без отдельного разрешения он ничего не обновляет и не загружает из сети**. Сначала доверенный Connect должен подготовить один конкретный серверный архив в `/opt/sovagrid-candidates/<sha256>` и показать администратору SHA-256 архива и манифест установленной версии. Затем клиент под тем же проверенным root SSH-подключением вызывает `python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/auto_update.py arm <archive-sha256> <current-manifest-sha256>`. Это внутренний контракт для графического клиента; пользователю не требуется вводить хеши в консоли. Команда заново проверяет действующую установку, архив, все исходники, совместимость включённых функций и доступность systemd-таймера до сохранения политики.

Политика `/etc/sovagrid/auto-update.json` принадлежит root и имеет режим `0600`. Она разрешает **ровно один** подготовленный архив для **ровно одной** установленной версии, истекает через 14 дней и не является подпиской на будущие релизы. Примерно каждые 15 минут служба пытается применить архив только если нет действующих или недавно завершившихся сессий панели, ожидающих команд и Telegram-подтверждений. Занятый сервер откладывает попытку. Если проверка или обновление провалились по другой причине, служба снимает разрешение и пишет состояние `needs_attention` в `/var/lib/sovagrid/auto-update-status.json`; повторного изменения до нового разрешения не будет. При успехе разрешение также удаляется. Для диагностики root может выполнить тот же скрипт с `status`; `disarm` немедленно снимает разрешение.

Установленный на сервере updater перед каждой попыткой повторно сверяет SHA-256 архива, манифест и исходники и использует тот же снимок и откат, что и ручное обновление Connect. Он не обращается к GitHub и не доверяет имени тега или URL. Клиент, запускающий первое обновление до этой версии, обязан поддерживать снимок и восстановление нового таймера; более старый updater получает отказ до изменений. Начиная с серверного пакета 0.8 автоматический путь удерживает короткую SQLite-блокировку записи под UID Hub, пока проверяет отсутствие работы и останавливает контейнер Hub. В пакете 0.9 он сначала получает от Agent подтверждение простоя по локальному Unix-сокету: оно охватывает команды, файловые и терминальные операции, сетевые проверки, активные загрузки и дочерние процессы. Подтверждение удерживается до проверенной остановки Agent, а блокировка SQLite снимается сразу после остановки Hub. При занятом Agent или Hub попытка откладывается; Agent старой версии без этого сокета требует однократного ручного обновления через Connect. Блокировка и подтверждение снимаются при гибели updater. Ручной путь обновления остался прежним. В Connect можно подготовить пакет, включить и выключить одноразовую политику и посмотреть её состояние. Подписанный канал будущих стабильных выпусков пока выключен: для него нужны доверенный ключ, стабильный пакет и отдельная проверка канала.

## Пользователи панели

В разделе «Настройки → Пользователи панели» администратор может создать отдельный вход, назначить роль наблюдателя/оператора/администратора, отключить доступ, сменить пароль или удалить пользователя. SSH и Telegram используют отдельные доступы. Последний действующий администратор защищён от отключения, удаления и понижения роли. Изменение прав или пароля закрывает только сеансы затронутого пользователя; уже переданное Agent задание может завершиться. При первом обновлении на эту схему сохраняются прежние данные входа и сессии единственного администратора. Откат восстанавливает предыдущую базу из снимка вместе с исходниками.

## Исходники

Расположите пять серверных репозиториев рядом:

```text
/opt/sovagrid-src/
  sovagrid-blueprint/
  sovagrid-hub/
  sovagrid-web/
  sovagrid-agent/
  sovagrid-vpn/
```

Можно клонировать публичные репозитории организации `sovagrid` по HTTPS на ноутбуке и передать папки на сервер. Другой вариант — клонировать `sovagrid-blueprint` на сервере, затем запустить `sudo env SOVAGRID_FETCH_MISSING=1 ./run.sh`. Отсутствующие исходники загружаются по HTTPS из `sovagrid` без GitHub-токена; `SOVAGRID_GITHUB_OWNER` позволяет явно выбрать другого владельца. Скрипт клонирует только отсутствующие папки и не делает `git pull` в существующих. Не вставляйте GitHub token в URL репозитория или командную строку.

Для последующего управления через Connect всё дерево `/opt/sovagrid-src` должно принадлежать root и не содержать символических ссылок или файлов, доступных на запись группе/остальным. При переносе через `rsync` с рабочего Mac используйте флаги без сохранения владельца и группы, например `-rltpv` вместо `-a`: иначе на Ubuntu может появиться UID локального пользователя Mac и графическое включение функций безопасно откажет.

## Первый запуск

```sh
cd /opt/sovagrid-src/sovagrid-blueprint
sudo ./run.sh
```

Установка работает без интерактивного терминала. Существующие Docker и Compose используются как есть. Если Docker или Compose отсутствуют, скрипт устанавливает только недостающий пакет из настроенных Ubuntu APT-репозиториев; `apt upgrade` и перезапуск действующего Docker не выполняются. На Ubuntu 26.04 пакет Compose из Ubuntu называется `docker-compose-v2`, в официальном Docker-репозитории — `docker-compose-plugin`. При отсутствии обоих установка прекращается с понятной ошибкой.

При первой установке создаётся случайный пароль администратора в `/etc/sovagrid/admin-password` (владелец root, режим `0600`). Скрипт выводит только путь, никогда сам пароль. Вход в Hub: пользователь `admin`, пароль из этого файла; при необходимости прочитайте его на доверенном терминале командой `sudo cat /etc/sovagrid/admin-password`. Содержимое пароля не передаётся через аргументы команды, переменные окружения или логи. Скрипт использует его один раз для регистрации местного Agent, после чего сохраняет ID и токен агента в `/etc/sovagrid/agent.json` и `/etc/sovagrid/agent.token` (владелец root, группа `sovagrid`, режим `0640`). Секреты находятся вне Git. При повторном запуске пароль, база, токен и ID сохраняются; существующий Agent не требует пароль администратора повторно. После входа пароль можно сменить в разделе «Настройки» панели: Hub проверит текущий пароль, завершит все сеансы и ожидающие задания, затем попросит войти с новым. Исходный файл `/etc/sovagrid/admin-password` **не обновляется** при смене через панель; он уже не подходит для входа и для регистрации *нового* Agent. Работа уже зарегистрированного Agent от этого не зависит.

### Вход с телефона через SSH

Откройте `https://<адрес-сервера>/sovagrid/monitoring/` на телефоне. На первой странице выберите «Подключиться по SSH», укажите пользователя сервера и пароль SSH либо приватный ключ через системный выбор файла. Перед отправкой данных нажмите «Проверить ключ сервера», сверьте SHA-256 отпечаток с независимым SSH-клиентом и подтвердите его. Панель закрепит отпечаток отдельно для этого адреса; при его изменении вход блокируется до ручной сверки. После успешного SSH-входа сервер выдаёт одноразовый пропуск в местный Hub, и отдельный пароль панели вводить не требуется. Вкладка «Войти в панель» сохраняет обычный вход по учётной записи Hub.

Администратор может изменить путь панели и действие на корневом `/` в разделе «Настройки → Доступ с телефона по HTTPS» либо через SovaGrid Connect. У новой публичной настройки вариант «Не открывать панель на /» оставляет панель на выбранном пути и отвечает 404 на корне и неизвестных адресах выделенного HTTPS-сайта. Существующая старая настройка, у которой `/` открывает панель, сохраняет это поведение до изменения администратором. Также доступны перенаправление `/` на путь панели и явный ответ 404. Стандартный `/sovagrid/monitoring/` остаётся рабочим alias при временном выборе другого публичного пути. Эти адреса не являются защитой от посторонних: вход и права проверяются отдельно. API остаётся на `/api/v1/*`, проверка здоровья — на `/healthz`.

На сервере без публичного HTTPS настройте отдельный путь в разделе «Настройки → Путь панели через SSH». Он действует только в локальном `127.0.0.1:8766` и не открывает новый порт в Интернет. Вариант «Оставить / как сейчас» сохраняет прежний локальный корень Web. После изменения Web может перезапуститься: интерфейс повторно проверяет `/api/v1/panel-location` и открывает подтверждённый путь без токена в URL; временный 503 означает ожидание, а не выбор старого пути. iOS/macOS и Android также проверяют найденный путь и его HTML/manifest при подключении.

Браузерный SSH-шлюз для входа в Hub подключается только к SSH этого же Ubuntu-хоста через закрытую Docker-сеть. Для выдачи пропуска пользователь должен быть `root` либо иметь право выполнить фиксированную команду через `sudo -n`; такой вход даёт административную роль местного Hub. Обычный SSH-пользователь без этих прав может пользоваться нативным SSH-клиентом, но не получает административную панель. Пароль и приватный ключ не сохраняются в Hub или браузерном хранилище. Форма не отправляет их с внешнего HTTP-адреса; используйте HTTPS либо локальный `127.0.0.1` через SSH-проброс.

### Добавление другого Ubuntu-сервера из веб-панели

После установки Hub администратор с доступом ко всем серверам открывает «Добавить сервер → Подключить по SSH». Панель отдельно показывает ключ SSH **целевого** сервера; его отпечаток нужно сверить независимо. Затем администратор вводит root SSH-пароль или выбирает приватный ключ и выполняет проверку состояния без изменений. Если Agent отсутствует, панель проверяет путь от целевого сервера к SSH-порту Hub и предлагает подготовить пакет. Подготовка записывает временный пакет на целевой сервер и закрытый журнал на Hub; запуск Agent требует отдельного подтверждения с показом Ubuntu, отпечатка Hub, версии пакета и ID операции. Вход с OTP/двухфакторным запросом в этом мастере пока не поддерживается.

Целевой сервер может иметь публичный IP, адрес в частной сети или маршрут через заранее настроенную сеть, если Hub способен подключиться к его SSH, а целевой сервер — к SSH-порту Hub. Сам мастер не открывает порт и не устраивает сетевой туннель через браузер. SSH-пароль и приватный ключ используются только для текущего запроса; при потере соединения выберите незавершённую запись и введите их снова. Незавершённые операции и проверенный пакет лежат в root-only `/var/lib/sovagrid/web-agent`; активные записи архивируются в закрытую историю. История ограничена 64 МиБ: при заполнении новая установка прекращается **до SSH-записи**, сохраняя незавершённые операции для восстановления. Браузер хранит лишь отпечаток публичного ключа для обнаружения его замены. Функция доступна только из HTTPS-панели или по локальному `127.0.0.1` через SSH-проброс. Если серверная часть ещё не обновлена, мастер покажет, что установщик недоступен.

`run.sh` включает отдельный root-owned контроллер `sovagrid-web-agent-control.service` с Unix-сокетом только для группы непривилегированного `ssh-gateway`. В контейнер не монтируются исходники, Docker socket или закрытый журнал. Контроллер заново проверяет действующий административный сеанс Hub на каждом действии; точные операции ограничены `prepare/apply/resume/cleanup/interrupt/status/list`. Установленные исходники сверяются с манифестом перед созданием частного пакета. Прямое обновление и снимок хоста блокируют новую операцию до завершения уже начатой, а резервная копия хоста включает временные пакеты, журнал и историю установок.

`ssh-gateway` — третий контейнер того же Compose-проекта без опубликованного порта. `run.sh` включает его только из управляемого `/opt/sovagrid-src` и после проверки здоровья создаёт root-only marker `/var/lib/sovagrid/.ssh-gateway-managed-by-run-sh`. При переходе со старого обновлятора, который сохраняет только Hub/Web, включение шлюза откладывается. Новый полный и Hub-only обновляторы сохраняют marker, исходный образ и точный состав контейнеров; при неудаче удаляют только контейнер, появившийся после снимка, и повторно проверяют маршрут входа через Web. Новый браузерный вход считается готовым после успешного ответа `/api/v1/browser-ssh/host-key` через Web, а не только после старта контейнера.

Для поэтапного запуска используйте `sudo ./run.sh --hub-only`: он установит Hub и Web, но не создаст Agent. После проверки выполните `sudo ./run.sh`.

Для управления отдельным стандартным WireGuard выполните `sudo ./run.sh --with-wireguard`. Скрипт при необходимости установит `wireguard-tools`, `iproute2` и системный модуль Python `cryptography`, а на Ubuntu с профилем AppArmor `wg-quick` добавит узкое правило для закрытых SovaGrid-конфигов. Он также установит root-owned локальный брокер `/run/sovagrid-vpn/control.sock` и узкий клиент `/usr/local/bin/sovagrid-vpn-ctl` для локального root. Agent распознаёт только фиксированную форму задания и отправляет запрос в сокет **из собственного основного процесса**; обычная команда от того же системного пользователя получает отказ по PID. Брокер разрешает только операции над собственными SovaGrid-инстансами, ограничивает время выполнения и передаёт клиентский профиль Agent только в зашифрованном виде. Служба Agent сохраняет `NoNewPrivileges` и свои ограничения. Установка не запускает VPN и не меняет контейнеры Amnezia. Root-only команды `recover` и резервный экспорт профиля описаны в [sovagrid-vpn](https://github.com/sovagrid/sovagrid-vpn); запускайте их из `/opt/sovagrid-src/sovagrid-vpn`. Статус после действия обновится таймером примерно за 30 секунд.

Пороги тревог изменяются администратором в разделе «Настройки»: CPU, память и заполненность диска от 1 до 100%, время без связи от 10 секунд до 24 часов, задержка подтверждения проблемы от 0 до 1440 минут. Hub хранит их в SQLite и применяет без перезапуска при следующей метрике или проверке отсутствия связи. `GET/POST /api/v1/monitoring/settings` требуют сеанс администратора; `POST` принимает пороги, `offline_seconds`, `revision` и `trigger_minutes`, отклоняя устаревшую редакцию с HTTP 409. Старый клиент может не передавать `trigger_minutes`: сохранённая задержка при этом остаётся прежней. Краткий всплеск не открывает инцидент; длительное превышение подтверждается новым измерением, потеря связи — периодической проверкой Hub. История показывает начало, восстановление и длительность. Обычное чтение и изменение через панель не требуют доступа к файлам или консоли сервера.

В разделе VPN панели выберите сервер с работающим Agent и разрешите для него команды в Hub; в локальной конфигурации Agent также должно быть `allow_remote_commands=true`. Для этой установки Hub и Agent находятся на одном Ubuntu-хосте. На выбранном хосте проверьте `systemctl is-active sovagrid-vpn-control.socket` и наличие `/run/sovagrid-vpn/control.sock`. Служба `sovagrid-vpn-control.service` запускается сокетом по запросу и может быть неактивна между запросами. Если выбран Agent другого сервера, ему нужен свой установленный брокер: этот `run.sh` не устанавливает его удалённо. Сводка `GET /api/v1/vpn` всегда собирается **на хосте Hub**, а не на выбранном Agent. Поэтому результат действия на другом сервере ищите в задании этого Agent; в сводке его WireGuard не появится.

Панель предлагает шесть действий над собственным WireGuard: подготовить инстанс (`create`, имя, свободный UDP-порт, частная подсеть, публичный IP или DNS), запустить его (`activate`), добавить клиента (`add-client`), отозвать клиента (`revoke-client`), получить защищённый профиль (`sealed-export`) и удалить инстанс (`remove`). `create` сохраняет закрытую конфигурацию, а интерфейс включается только отдельным `activate`. Перед отправкой каждого действия показываются сервер и параметры; `remove` требует дополнительно ввести точное имя инстанса. Панель посылает `POST /api/v1/servers/{id}/vpn/actions` с уникальным `Idempotency-Key`, показывает ID и состояние задания. Если ответ потерян, повтор в том же окне использует тот же ключ; после закрытия окна сначала проверьте задания и состояние. Hub сохраняет тип структурированного задания, Agent повторно проверяет фиксированные аргументы и обращается прямо к root broker без shell.

Для `sealed-export` откройте панель через HTTPS или доверенный `127.0.0.1` после SSH-проброса. Укажите существующие инстанс и клиент, подтвердите действие и дождитесь завершения задания **в той же вкладке**. Затем нажмите «Скачать .conf» либо системную кнопку передачи файла на телефоне. Вкладка создаёт временный ECDH P-256 ключ; root broker шифрует профиль AES-256-GCM до отправки Agent. В результате задания Hub хранит только шифротекст; закрытый ключ профиля и открытый файл туда не поступают. После обновления или закрытия вкладки временный ключ теряется, поэтому для повторного скачивания потребуется новая выдача. Скачанный `.conf` содержит рабочий закрытый ключ клиента: храните и передавайте его как секрет. Root-only `export-client` остаётся резервным способом на целевом хосте.

Управление профилями существующего AmneziaWG и WireGuard выделено в отдельный opt-in механизм. `run.sh` не устанавливает и не запускает его брокер. Администратор может пройти веб-мастер на **хосте открытой панели** либо на другом Ubuntu-сервере, к которому Hub имеет прямой SSH-доступ: сверить ключ хоста, посмотреть состояние, проверить существующий контейнер, подключить его к SovaGrid, установить брокер и отдельно включить управление в окно обслуживания. Для нового Agent-only сервера Web Agent отдельно подготавливает исходники `sovagrid-vpn` из проверенного пакета после SSH-входа и сравнения хешей. Подготовка временно передаёт пакет в закрытый каталог, устанавливает два root-owned дерева исходников с журналом отката и не запускает VPN-службы или контейнер. Предпросмотр возвращает хеш исходников и снимок состояния; применение требует эти же значения. Если операция прервалась, отдельное восстановление откатывает незавершённую замену. Обновление исходников останавливается, когда уже установлен управляющий VPN-брокер; для него нужен согласованный путь обновления брокера. Через промежуточный SSH-хост веб-мастер пока не ходит, для такого маршрута используйте Connect. Каждый шаг требует повторного SSH-входа и новой сверки снимка; мастер не создаёт VPN-контейнер. Панель оставляет кнопки создания, защищённого экспорта и отзыва профиля выключенными, пока брокер не включён на выбранном сервере. Подготовка, ограничения по протоколам и восстановление описаны в [AMNEZIA_ADMIN.md](https://github.com/sovagrid/sovagrid-vpn/blob/main/AMNEZIA_ADMIN.md).

После подготовки исходников отдельный веб-шаг устанавливает управляемый root-брокер WireGuard на выбранном Agent. Он требует нового SSH-входа, сверки двух ревизий и явного подтверждения; VPN-интерфейс при этом не запускается. Формат запросов, восстановление и ограничения описаны в [контракте Web Agent](deploy/WEB_WIREGUARD_CONTROL.md).

## Интерактивный терминал в панели

Для терминала на хосте с Agent выполните `sudo ./run.sh --with-terminal` из каталога blueprint. Ключ устанавливает локальный PTY broker, создаёт отдельную учётную запись `sovagrid-shell` и включает в `/etc/sovagrid/agent.json` оба локальных флага: `allow_remote_commands=true` и `allow_interactive_terminal=true`. Он не включается при обычной первой установке. После установки следующие запуски `run.sh` с Agent обновляют broker, сохраняя флаги; `--hub-only` остаётся доступным. На другом Ubuntu-хосте брокер и флаги следует установить там, где работает нужный Agent. Затем в панели разрешите команды для выбранного сервера в Hub и откройте его терминал.

Терминал и его broker работают от имени **`sovagrid-shell`**, отдельного от `sovagrid` пользователя, под которым Agent хранит токен. Systemd открывает Unix socket и запускает broker без Linux capabilities. Broker проверяет UID клиента, создаёт PTY и передаёт Agent только файловый дескриптор. Он не принимает произвольные команды и не открывает сетевой порт. Agent подключается к Hub сам через HTTPS; браузер использует тот же origin, что и панель. `sovagrid-shell` не входит в группу `sovagrid`, не читает `/etc/sovagrid/agent.token` и не имеет root/sudo. Для привилегированной настройки сервера используйте отдельное SSH-подключение.

Проверьте установку командами `systemctl is-active sovagrid-terminal-control.socket sovagrid-agent`, `test -S /run/sovagrid-terminal/control.sock`, `id sovagrid-shell` и `sudo -u sovagrid-shell test ! -r /etc/sovagrid/agent.token`. Служба `sovagrid-terminal-control.service` запускается сокетом по запросу и может быть неактивна между запросами. В панели проверьте ввод, вывод, изменение размера и закрытие. Один Hub допускает до четырёх терминалов одновременно, по одному на сервер; при 90 секундах без запросов от браузера или через 30 минут сеанс закрывается. Потоки ввода и вывода остаются только в ограниченной памяти Hub и не записываются в базу и аудит. Выход из Hub, смена пароля, отзыв токена Agent и отключение команд закрывают терминал. После перезапуска Hub сеанс потребуется открыть заново. Подробный HTTP-контракт приведён в [Hub API](../sovagrid-hub/API.md).

## Файловый менеджер в панели

Для первого безопасного каталога выполните `sudo ./run.sh --with-files`. Скрипт создаёт `/var/lib/sovagrid-agent/files` с владельцем `sovagrid` и правами `0700`, затем включает `allow_remote_commands=true`, `allow_file_manager=true` и `file_roots.workspace` с точным путём в `/etc/sovagrid/agent.json`. Существующие другие корни сохраняются; если имя `workspace` уже занято другим путём, установка прекращается без замены этого значения. Обычный запуск `run.sh` не включает файловый доступ сам. В Hub также разрешите команды для выбранного сервера.

Раздел «Файлы» через исходящее HTTPS-соединение Agent показывает разрешённые каталоги, читает и правит обычные UTF-8 файлы до 8 КБ, загружает двоичные файлы до 4 МБ и скачивает до 32 МБ частями по 64 КБ. Скачивание проверяет SHA-256 и ETag; загрузка и замена требуют подтверждения. При замене проверяется версия файла, при создании файл не перезаписывается, если появился параллельно. Agent работает без root, не следует по символическим ссылкам и отвергает специальные файлы и жёсткие ссылки. Содержимое находится только в ограниченной памяти Hub и Agent, не записывается в базу или журнал; аудит содержит тип операции и хеш пути. Доступ к другим каталогам настраивается вручную через явный `file_roots` на соответствующем Agent и отдельное разрешение записи в его systemd unit. Не добавляйте в корни `/etc/sovagrid`, закрытые ключи VPN и данные Hub. После установки проверьте `systemctl is-active sovagrid-agent` и создайте тестовый файл от имени `sovagrid` внутри разрешённого каталога; он должен появиться в панели.

## Журналы выбранных systemd-служб

В Connect при первой установке либо через «Включить функции…» отметьте журналы и введите **точные** имена служб с окончанием `.service`, по одному в строке: например, `ssh.service` и `nginx.service`. Допустимо от 1 до 16 уникальных имён; повтор, произвольные аргументы, шаблоны и другие типы unit отклоняются. В окне подтверждения Connect покажет полный список. На уже установленном сервере он **целиком заменяет** предыдущий список. Альтернативный запуск для администратора: `sudo ./run.sh --with-journal --journal-unit ssh.service --journal-unit nginx.service`. Чтобы полностью выключить функцию без консоли, в том же окне выберите «Полностью выключить журналы» и подтвердите; ручной эквивалент — `sudo ./run.sh --disable-journal`. Отключение сначала атомарно снимает разрешения Agent, затем останавливает socket и broker и удаляет только управляемые policy и systemd units. Если broker уже не работает, его не запускают для выключения. Отдельная учётная запись остаётся без работающей службы и общего доступа к журналу. Без этих явных флагов обычный повторный запуск сохраняет настроенное состояние. `--hub-only` с флагами журнала отклоняется.

Скрипт создаёт отдельного пользователя `sovagrid-journal`, закрытый файл `/etc/sovagrid-journal/units.json` с владельцем `root:sovagrid-journal` и режимом `0640`, а также socket `sovagrid-journal-control.socket`. Только **служба broker** получает дополнительную группу `systemd-journal`. Пользователь Agent `sovagrid`, который может исполнять обычные задания, не получает `systemd-journal` или `adm`; установщик отказывает, если у него уже есть одна из этих широких групп. Broker проверяет UID клиента и перечень служб независимо от настроек Agent. Agent включает `allow_remote_commands=true`, `allow_systemd_journal=true` и `journal_units` только после готовности broker. В Hub администратор отдельно разрешает удалённые команды для выбранного сервера. Без всех этих условий журнал не выдаётся. Вывод ограничен последними строками и не сохраняется в истории метрик.

Для проверки после установки: `systemctl is-active sovagrid-journal-control.socket sovagrid-journal-control.service sovagrid-agent`, `stat -c '%U:%G:%a' /etc/sovagrid-journal/units.json` и `id -nG sovagrid`. Должны быть активны обе службы и Agent, у policy — `root:sovagrid-journal:640`, у Agent отсутствуют группы `systemd-journal` и `adm`. Для чтения через панель выберите сервер и одну из разрешённых служб. Если имя службы отсутствует в списке, сервер выключен, broker не отвечает или разрешение Hub снято, запрос отклоняется без fallback на произвольную команду.

## Управление systemd-службами

В разделе «Службы» администратор сначала проверяет состояние выбранной `.service`; `start`, `stop` и `restart` требуют свежего успешного результата и отдельного подтверждения в интерфейсе. Корневой broker принимает только заранее разрешённые действия из root-owned `/etc/sovagrid-service/units.json` или отдельной политики локального Agent. Изменение служб выключено по умолчанию. Для SSH, сети, Docker, VPN, SovaGrid и туннелей изменение запрещено даже в ошибочной политике. Broker проверяет системные алиасы перед действием и принимает запрос только от PID основного процесса Agent. Если результат изменения потерян или пришёл тайм-аут, сначала запросите новый `status`.

Hub отделяет структурированные задания служб, WireGuard и Amnezia от произвольных команд Web/Telegram. Старые ожидающие задания с их маркерами отменяются при выдаче после обновления. Обычная команда не получает прямой доступ к root broker даже при том же UID, что и Agent. При полном обновлении одновременно перезапускаются Agent и брокеры; Hub-only обновление сохраняет внешний Agent и его туннель, но может обновить локальный Agent и его service broker.

## Доступ с телефона и компьютера

Compose публикует **только** `127.0.0.1:8766` (веб-панель и API) и `127.0.0.1:8767` (локальный HTTPS для Agent). Hub в Docker-сети не публикует порт на хосте.

В приложении SovaGrid для iPhone/iPad или Android сохраните SSH-профиль **своего** Ubuntu-сервера: адрес или DNS-имя, порт, имя пользователя и ключ либо пароль. Сверьте отпечаток SSH-ключа по независимому каналу. Раздел «Панель» создаст временный локальный проброс к `127.0.0.1:8766` на выбранном сервере и откроет Web UI. Если на этом сервере установлен Hub, root/sudo SSH может выдать одноразовый пропуск для входа в местную панель; отдельные логин и пароль Hub доступны как другой способ входа. Для просмотра панели через туннель не требуется публиковать порт 8766 в интернете.

Для SSH-доступа через промежуточный хост создайте профиль с двумя узлами:

| Поле | Значение |
| --- | --- |
| Промежуточный SSH-хост | Адрес, порт и пользователь вашего промежуточного сервера |
| Конечный SSH-хост | Адрес и порт, доступные с промежуточного сервера; пользователь целевого Ubuntu-хоста |

Приложение отдельно проверит SSH-ключ и учётные данные каждого узла. Если целевой сервер доступен через обратный туннель, его запуск и восстановление настройте на стороне целевого сервера; SovaGrid использует уже работающий маршрут. Панель целевого сервера доступна после установки на нём собственного Hub.

Для доступа к панели с компьютера откройте SSH-туннель:

```sh
ssh -L 8766:127.0.0.1:8766 SSH_USER@SERVER_ADDRESS
```

После этого откройте `http://127.0.0.1:8766/sovagrid/monitoring/` на своём компьютере. Локальный корень `/` продолжает работать для старых закладок. При настройке собственного пути используйте адрес, показанный в «Настройки → Путь панели через SSH»; `/api/v1/*` остаётся без префикса. Веб-панель и API находятся на одном origin. Локальный TLS Caddy для Agent выпускает собственный CA; при обычной установке `run.sh` копирует только публичный сертификат в `/etc/sovagrid/hub-ca.pem`. При `--hub-only` сертификат нового Hub хранится отдельно в `/var/lib/sovagrid/local-hub-ca.pem`, чтобы сохранить CA прежнего Agent. Закрытый ключ CA остаётся в `/var/lib/sovagrid/caddy`, доступном только выделенному пользователю контейнера и root.

Публичный HTTPS — отдельная настройка через Connect или Web: можно указать собственный домен либо статический публичный IP и выбрать путь панели. Корневой `/` не меняется без явного выбора администратора. Порты `8766` и `8767` сохраняются только на `127.0.0.1` и не публикуются на `0.0.0.0`.

## Проверка после установки

```sh
sudo docker compose --env-file /etc/sovagrid/deploy.env -f deploy/compose.yaml ps
sudo ss -ltnp | grep -E ':8765|:8766|:8767'
curl -fsS http://127.0.0.1:8766/healthz
curl --cacert /etc/sovagrid/hub-ca.pem -fsS https://localhost:8767/healthz
systemctl is-active sovagrid-agent
journalctl -u sovagrid-agent -n 20 --no-pager
```

Если установлен `--with-terminal`, дополнительно проверьте `systemctl is-active sovagrid-terminal-control.socket`, наличие `/run/sovagrid-terminal/control.sock` и отсутствие читаемости Agent token от имени `sovagrid-shell`.

Ожидается два контейнера проекта `sovagrid`, обе публикации только на `127.0.0.1`, а слушающего `8765` на хосте нет. Agent отправляет первый образец при запуске, затем каждые 30 секунд. В веб-панели сервер должен стать онлайн; его общая память и объём корневой файловой системы должны совпадать с `MemTotal` из `/proc/meminfo` и `df -B1 /` на Ubuntu. Разделы `/proc`, `/sys` и другие псевдофайловые системы исключены из детального списка.

Для нового управляемого Ubuntu-хоста сбор включается отдельно через `run.sh --with-containers`; состояние Docker и Podman обновляет таймер примерно раз в 30 секунд. Agent и Hub не получают Engine socket; снимок содержит только имя, образ, ID, состояние, health, число перезапусков и ограниченные показатели CPU/RAM. Пустой или недоступный Podman-источник виден отдельно, а данные старого снимка помечаются устаревшими. Журналы читает отдельный ограниченный broker. Для действий Docker нужна отдельная политика с точным ID: в Connect администратор выбирает незапрещённый контейнер, сверяет статус, разрешает только выбранные `status/start/stop/restart` и затем может отключить разрешение. Hub и Agent повторно проверяют ID и состояние перед действием; защищённые контейнеры SovaGrid и Amnezia недоступны для изменений. Рабочие контейнеры не получают новых прав по умолчанию.

На сервере с собственным Hub и сохранённым внешним Agent можно использовать отдельный локальный root collector. В Connect выберите проверенный root/sudo SSH-профиль целевого сервера и «Локальный инвентарь контейнеров», затем просмотрите состояние. Включение требует подтверждённого пакета и неизменного состояния; процесс установит `sovagrid-container-inventory-local.timer` и запишет очищенный снимок в `/var/lib/sovagrid-containers-local/snapshot.json`, доступный только группе `sovagrid-local`. Если ответ потерян, Connect заново читает состояние и предлагает восстановить операцию. `preview`, `enable --expected-state HASH`, `disable --expected-state HASH` и `recover` доступны root в `/opt/sovagrid-src/sovagrid-blueprint/deploy/local_container_inventory.py`. Внешний Agent и SSH-туннель не переключаются. Этот режим не выдаёт права на изменение Docker-контейнеров.

Отдельный `sovagrid-vpn-status.timer` раз в 30 секунд собирает два независимых источника: состояние известных Amnezia-контейнеров и состояние собственных WireGuard-инстансов SovaGrid. Это операция только чтения. Очищенный снимок находится в `/var/lib/sovagrid/vpn/status.json` и доступен Hub через отдельный read-only mount. Проверьте `systemctl status sovagrid-vpn-status.timer` и после входа `GET /api/v1/vpn`: в ответе `vpn.source_status` относится к Amnezia/Docker, а `vpn.managed.source_status` — к WireGuard. При исправных источниках оба значения — `ok`; пустой список `vpn.managed.instances` нормален, если инстансы ещё не созданы. Ошибка или устаревшие данные одного источника не скрывают другой в панели. Для WireGuard выводятся только имя, интерфейс, порт, подсеть, состояние и число клиентов; ключи, адреса пиров и профили в снимок не попадают. Существующие Amnezia-контейнеры не изменяются, Hub и Agent не получают Docker socket.

Установщик использует отдельную Docker-сеть `172.30.253.0/28`. Перед установкой проверьте, что она не пересекается с сетями Docker, VPN и локальной маршрутизацией вашего хоста. Статический IP веб-прокси нужен для доверенного заголовка клиентского IP в Hub.

## Telegram

Бот отключён до настройки. Создайте его через BotFather, откройте панель через SSH-проброс, войдите как администратор и в разделе «Telegram» вставьте токен. Hub сохраняет его отдельным файлом `/data/telegram-bot-token` в своём закрытом каталоге данных и запускает опрос Telegram без перезапуска Docker-контейнера. В интерфейсе сохранённый токен не отображается. На Ubuntu этот файл находится в `/var/lib/sovagrid/hub/telegram-bot-token`; включите каталог Hub в защищённую резервную копию. Токен не вставляйте в командную строку, URL или чат.

Уведомления о тревоге, восстановлении и напоминания после обслуживания записываются в SQLite вместе с изменением инцидента. Они переживают перезапуск Hub и временное отсутствие токена; отправка повторяется с ограниченной задержкой, а перед ней перепроверяются привязка, роль и окно обслуживания. В разделе Telegram видно число ожидающих уведомлений. Если Telegram принял сообщение, но HTTP-ответ потерян, повтор может создать дубликат. Результаты команд и сообщения о привязке пока используют очередь в памяти.

Затем откройте своего бота в личном чате и отправьте `/start` или `/connect`. В разделе Telegram панели появится ожидающая заявка с именем, Telegram username и числовым ID; эти сведения пришли от Telegram и нужны для проверки личности перед предоставлением доступа. Администратор выбирает роль `viewer`, `operator` или `admin` и подтверждает или отклоняет заявку. Ни одному пользователю доступ не выдаётся автоматически. Ручной ввод ID и резервный способ через CLI доступны для диагностики:

```sh
sudo docker compose --env-file /etc/sovagrid/deploy.env \
  -f deploy/compose.yaml -f deploy/compose.telegram.yaml \
  exec hub python3 -m sovagrid_hub --db /data/hub.sqlite \
  bot-user add --user-id 123 --chat-id 123 --role admin
```

Замените оба числовых ID. Роли: `viewer` получает состояние и тревоги, `operator` также подтверждает тревоги, `admin` может запросить команду с отдельным подтверждением. После привязки любая из этих ролей может отправить `/vpn` в личном чате и получить сводку Amnezia и WireGuard без ключей и клиентских профилей. Команда `/checks` показывает фиксированные состояния HTTP/TCP/DNS без адресов целей, ожидаемых IP и произвольных названий проверок. Произвольные команды по умолчанию отключены как в Hub, так и в Agent; для их включения нужны оба переключателя, описанные в [README Hub](../sovagrid-hub/README.md) и [README Agent](../sovagrid-agent/README.md). Включать их следует только для доверенных администраторов: команда выполняется от имени пользователя Agent и может читать доступные ему файлы.

Старый способ с root-owned `/etc/sovagrid-hub/bot.token` также поддерживается. Если файл уже существует, `run.sh` подключает [compose.telegram.yaml](deploy/compose.telegram.yaml) с read-only mount; панель показывает, что токеном управляет хост, и не заменяет его. Чтобы пользоваться вводом из панели, не создавайте этот внешний файл при новой установке.

## Повторный запуск и ограничения

Повторный `sudo ./run.sh` обновляет только образы и службу SovaGrid, не удаляет базу, токены или чужие контейнеры. Он не запускает `docker system prune`, `compose down --volumes`, `apt upgrade` или команды изменения Amnezia. Состояние Hub хранится в `/var/lib/sovagrid/hub`; сохраняйте его в защищённой резервной копии вместе с `/etc/sovagrid` и `/var/lib/sovagrid/caddy`.

### Резервные копии Hub из панели

На управляемой установке из root-owned `/opt/sovagrid-src` новый `run.sh` устанавливает узкий host-root broker: `sovagrid-hub-backup-control.socket` и `.service`. Его Unix-сокет `/run/sovagrid-hub-backup/control.sock` доступен только UID Hub через группу `sovagrid-hub`; в контейнер Hub монтируется только каталог сокета для чтения. Каталог `/var/lib/sovagrid/backups` с копиями, root-only журналом создания `.broker-requests` и журналами восстановления остаётся исключительно на хосте. API Hub допускает только администратора с доступом ко всем серверам: список, проверку, создание снимка и подтверждённое восстановление по UUID. Broker проверяет UID клиента, свободное место, конкретную копию и один управляемый контейнер Hub. Для восстановления он работает на хосте после остановки Hub, затем запускает тот же контейнер и проверяет его здоровье. Потеря HTTP-ответа не повторяет замену данных: состояние и история читаются по сохранённому UUID после повторного входа. Если состояние неоднозначно и Hub оставлен остановленным, веб-API недоступен; в Connect есть отдельное подтверждаемое исправление через root SSH.

Socket запускается **до** `docker compose up`; его отсутствие прерывает установку вместо запуска панели с неправильным mount. Для ручного checkout вне `/opt/sovagrid-src` функция откладывается, так как root-служба не должна исполнять редактируемые пользователем исходники. Если обновление запущено прежним updater без снимка новых unit-файлов и журнала, первый переход также откладывает включение broker; следующий переход под новым updater сможет его включить. При независимом обновлении Blueprint с прежним Hub, где ещё нет кода broker, он тоже откладывается до обновления Hub. Если broker уже установлен, updater без поддержки снимка отклоняется. Новый полный и Hub-only updater включают marker, оба unit-файла и `.broker-requests` в откат, не копируя пользовательские резервные копии; общий lock `/opt/sovagrid-candidates/.lock` сериализует создание снимка с обновлением и offline-восстановлением.

Тот же root broker предоставляет полному администратору метаданные закрытых [копий управляемого состояния хоста](HOST_BACKUP.md): план, список, проверку, запуск и восстановление служб. Архивы не скачиваются через Web. Для фоновой операции установщик заранее создаёт `/var/lib/sovagrid-host-backup-operations` с правами `root:root 0700`. Этот же broker применяет публичный и локальный путь Web. После обновления проверьте `systemctl show -P TasksMax sovagrid-hub-backup-control.service` и API статуса панели.

На одноразовой Linux-среде проверяются соединение с root broker через read-only bind под UID Hub, отказ другим UID, атомарная замена каталога и восстановление после принудительного обрыва. Полная проверка обновления с откатом и свободного места нужна перед установкой на свой сервер. Broker отказывает до остановки Hub, если места недостаточно.

### Полная копия управляемого состояния хоста

После установки общего серверного пакета откройте в Connect **«Полные копии сервера…»** через проверенный root SSH-маршрут. Мастер сверяет весь установленный source manifest, показывает точный список служб и контейнеров, которые временно остановит, и требует подтверждение. Операция получает UUID до остановки, работает отдельно от SSH-сеанса, создаёт root-only архив в `/var/lib/sovagrid-host-backups` и возобновляет только ранее активные компоненты после проверки Hub и Web. При обрыве соединения Connect показывает состояние сохранённого UUID; если восстановление служб не завершилось, отдельная кнопка запускает только `recover`, без повторного снимка. Внешний Agent, обратный SSH-туннель и сторонняя VPN-маршрутизация не входят в обновляемый локальный Hub. Команды, лимиты, состав архива и ограничения описаны в [HOST_BACKUP.md](HOST_BACKUP.md). Архив содержит секреты и не выдаётся через Web API. `host_restore.py clean-plan <id>` уже может проверить перенесённую пару архивов и занятые пути чистого Ubuntu-хоста без распаковки; применение восстановления и перенос Docker-образов пока не реализованы.

Если весь Ubuntu-сервер отключится, размещённый на нём Hub не сможет отправить тревогу. Для этого нужен внешний наблюдатель на другом хосте.

## Сетевые проверки Agent

Протокол checks v1 работает отдельно от очереди команд, PTY, файлов и отправки метрик. После обновления Hub, Agent и Web администратор задаёт цели через форму обзора сервера. Дополнительный root broker и разрешение произвольных команд для проверок не требуются. Agent использует два фиксированных worker и не более двух изолированных Python-процессов с общим сроком 1–10 секунд, включая DNS. На Linux helper завершается и при потере родительского Agent.

До 16 целей на сервер; интервал 60–3600 секунд, история — до 60 результатов на цель. HTTP/HTTPS выполняет только GET, не следует перенаправлениям и не читает тело. Суммарные заголовки ограничены 32 КиБ. HTTPS использует системное доверие и проверку имени. Для домашнего сервиса администратор может выбрать в форме один сертификат доверенного CA в PEM или DER; его DER-представление ограничено 1536 байтами. Проверка цепочки и имени остаётся обязательной. TCP только устанавливает соединение, без прикладных данных. DNS проверяет запись A или AAAA через системный resolver выбранного Agent. Можно указать ожидаемый IP той же семьи: проверка успешна, если он есть среди ответов; без него достаточно любого корректного ответа. Адреса ответа не отправляются в Hub, историю или Telegram. Явно заданные private/loopback-цели разрешены, unspecified/multicast отклоняются, диапазоны не сканируются. URL с учётными данными, query или fragment не принимаются.

Hub не подключается к целям. Он выдаёт Agent lease на 90 секунд, проверяет текущий токен, сервер и ревизию конфигурации; изменение настроек или ротация токена отменяет старый lease. Настройки защищены общей ревизией от перезаписи другой вкладкой. Наблюдатели и операторы получают только имена, типы, расписание и фиксированные результаты без URL/host/port или ожидаемого DNS-адреса. При старом Hub Agent откладывает повторы, продолжая метрики и команды; при старом Agent панель показывает отсутствие запросов функции. Инциденты HTTP/HTTPS, TCP и DNS проходят общие правила задержки, окна обслуживания и уведомления о восстановлении; Telegram получает короткий ID проверки, но не её имя или цель. Поля и маршруты описаны в [API Hub](https://github.com/sovagrid/sovagrid-hub/blob/main/API.md). Метки результатов и инцидентов хранятся как UTC Unix seconds; браузер показывает время событий в часовом поясе устройства.

Для HTTPS-проверки администратор может отметить «Предупреждать об истечении HTTPS-сертификата» и выбрать 1–90 дней. Отдельный TLS-инцидент возникает только по подтверждённому сроку сертификата после общей задержки тревог. Если новый результат не содержит проверенного срока, существующий инцидент не объявляется восстановленным. Панель независимо выделяет сертификаты, до истечения которых осталось не более 14 дней. Настройка выключена по умолчанию и не передаётся в Agent: он по-прежнему выполняет ту же проверку.

В «Настройках» администратор может включить общее правило использования inode корневой файловой системы `/`: порог больше 0 и до 100%, задержка 30 секунд — 24 часа. Каждый Agent уже передаёт счётчики inode в `details.filesystems`. Hub сверяет процент со счётчиками и не делает вывод о восстановлении, если корневой раздел или согласованные значения отсутствуют. Тревога отправляется через те же окна обслуживания и долговечную очередь Telegram; правило выключено по умолчанию. Наблюдатели и операторы видят сохранённое правило, но менять его может только администратор с полным доступом.

В обзоре каждого сервера можно включить отдельные правила для смонтированных локальных файловых систем: занятое место и inode. Администратор выбирает точку из свежего полного отчёта Agent, задаёт порог 1–100% и общую задержку подтверждения 0–86400 секунд. Изменения защищены ревизией; новое правило нельзя создать по старому или неполному списку. Agent передаёт признак усечения, когда часть файловых систем не помещается в отчёт или счётчик недоступен. Hub пересчитывает процент из исходных счётчиков и не объявляет восстановление, если строка исчезла, устарела или противоречива. Правила выключены по умолчанию, проходят окна обслуживания и долговечную очередь Telegram; бот получает короткий хеш вместо пути монтирования.
