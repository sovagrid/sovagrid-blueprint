# Подписанный канал серверных обновлений

В `deploy/release_feed.py` реализована проверка будущих выпусков и локальный контракт `status`/`enable`/`disable`. Актуальные [подписанная стабильная лента и её цепочка](https://github.com/sovagrid/sovagrid-update-feed) опубликованы в отдельном репозитории. Hub и Web показывают состояние и дают глобальному администратору включить или отключить подписку в разделе «Настройки → Обновления этого сервера» с отдельным подтверждением. Публичный ключ закреплён в исходниках, а закрытый хранится вне Git, CI и управляемых серверов. **Подписка каждого сервера выключена по умолчанию**; публикация ленты не создаёт на нём конфигурацию и не меняет установленную версию. `run.sh` устанавливает systemd units на новой установке и при обновлении под новым worker. При первом переходе со старого worker установка units откладывается до следующего контролируемого запуска `run.sh` или обновления, потому что старый worker не умеет восстанавливать их при откате. Если feed-файлы уже есть, старый worker отказывает до изменений. Существующий `sovagrid-auto-update.timer` продолжает работать только с одним заранее одобренным архивом.

В SovaGrid 1.0.0 подписанный канал выбирает отдельный backend для полного сервера или **поддерживаемой, полностью активированной Hub-only promotion**. Во втором случае используются существующие `hub_only_update.py` и `hub_only_auto_update.py`: внешний Agent, его данные и SSH-туннели не входят в изменяемый снимок и не перезапускаются. Схема подписанной ленты и архив остаются общими. Установленный старый `server-v0.14.1` отказывает для Hub-only; сначала нужен согласованный ручной переход на новый серверный пакет.

Новая root-only opt-in конфигурация сохраняет `layout:"full"` либо `layout:"hub_only"`. Старый четырёхполевой конфиг означает исключительно `full` и не разрешает обновление появившейся promotion. Режим и отпечатки её закрытого состояния входят в CAS `state_revision`; публичный JSON статуса сохраняет прежние поля для совместимости клиентов. После смены режима подписку нужно отключить и включить заново с подтверждением. Неполная, небезопасная или неподдерживаемая promotion отказывает до сетевой загрузки и подготовки кандидата; она никогда не считается полным сервером. `status` и подтверждаемое отключение остаются доступны.

Перед загрузкой пакета и непосредственно перед выдачей разрешения режим проверяется повторно. Операции используют порядок блокировок policy → installation → promotion → candidate. Discovery отпускает installation/promotion перед вызовом arm; необязательный CLI `arm ARCHIVE CURRENT --layout full|hub_only` повторяет проверку под policy-блокировкой и отзывает только своё новое разрешение при смене режима. Прежний трёхаргументный CLI и пятизначная структура одноразовой политики сохранены. Сам updater снова проверяет свой режим под installation-блокировкой перед изменениями. Обычный one-candidate таймер не скачивает выпуски самостоятельно.

Текущие ограничения Hub-only worker сохраняются: чужие файлы, незавершённые внешние операции и неподдерживаемые функции не включаются молча ради подписки. Интерфейс сообщает о необходимости проверки текущей конфигурации, не обещая поддержку любой promotion.

## Контракт канала

Источники жёстко заданы в коде:

- `https://raw.githubusercontent.com/sovagrid/sovagrid-update-feed/main/stable.json` — точный адрес подписанного документа в [отдельном публичном репозитории](https://github.com/sovagrid/sovagrid-update-feed). Документ и его подпись опубликованы вместе; каждая запись цепочки связывает точные манифесты установленного и нового выпусков. Хранить его в Blueprint нельзя: `package_server.py` включил бы его в архив, и SHA-256 архива рекурсивно зависел бы от самого себя. В репозитории есть [publisher и проверка с временным ключом](https://github.com/sovagrid/sovagrid-update-feed); production-подпись создаётся отдельно, вне CI и сервера.
- тот же путь с окончанием `.sig` — ровно 64 байта отсоединённой подписи Ed25519 над **исходными байтами** JSON;
- архив `https://github.com/sovagrid/sovagrid-blueprint/releases/download/server-v<VERSION>/SovaGrid-server-source.tar.gz`. Версия строго `MAJOR.MINOR.PATCH` без ведущих нулей. Манифест не может задавать URL или команду.

GitHub описывает `browser_download_url` публичного release asset и возможность редиректа при выдаче архива в [документации Release assets](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28). Опубликованный архив `v0.14.1` скачан и сверен в интеграционных тестах установки и ручного обновления. Его установленные feed/auto/worker также прошли [настоящее автоматическое применение следующего согласованного кандидата и откат](https://github.com/sovagrid/sovagrid-blueprint/actions/runs/41298983265) на одноразовой Ubuntu с временным ключом и моделью HTTPS-ответов. Эта проверка рабочего кода использует одноразовый ключ; актуальная production-цепочка доступна в [репозитории ленты](https://github.com/sovagrid/sovagrid-update-feed). GitHub может изменить CDN-домен; в этом случае загрузка остановится до review и обновления allowlist.

Проверяющий не передаёт учётные данные, не использует переменные прокси, требует TLS и принимает редиректы только на `github.com`, `release-assets.githubusercontent.com` и `objects.githubusercontent.com`. CDN может добавлять временный query-параметр; он не используется как вход для выполнения команд. Нет поддержки произвольного зеркала, приватного GitHub-релиза или GitHub API с токеном.

Схема подписанного документа:

```json
{
  "format": 1,
  "channel": "stable",
  "key_id": "REVIEWED_KEY_ID",
  "issued_at": 1800000000,
  "expires_at": 1800600000,
  "releases": [
    {
      "sequence": 1,
      "version": "0.3.10",
      "from_manifest_sha256": "64 lowercase hex characters",
      "to_manifest_sha256": "64 lowercase hex characters",
      "archive_sha256": "64 lowercase hex characters",
      "archive_size": 12345678
    }
  ]
}
```

Это иллюстрация полей, не публикуемый манифест. Выпуски идут строго по возрастающим `sequence` и версии; `to_manifest_sha256` одной записи совпадает с `from_manifest_sha256` следующей. Можно оставить в ленте цепочку до 32 выпусков, чтобы отстающий сервер проходил их по одному. `issued_at` и `expires_at` — Unix seconds в UTC, независимо от страны и часового пояса сервера. Другая страна не объясняет расхождение UTC-часов на 165 секунд: это отдельный вопрос синхронизации. Время сервера должно быть достаточно точным: откат более чем на пять минут или просроченный манифест вызывает отказ. Подписанный документ действует максимум 30 дней и требует повторной подписи при продлении.

Проверяющий отвергает неизвестные поля, дубликаты JSON-ключей, некорректную версию, неподходящий исходный манифест и повтор старого `sequence`/версии. Он ограничивает размер ленты 32 КБ, архива 64 МиБ, распаковки 256 МиБ и число элементов 4096. SHA-256 архива и манифеста новой версии сверяются **до** передачи кандидата действующему `auto_update.py`. Из архива принимаются только обычные файлы и каталоги с безопасными именами и правами. Затем существующий transaction worker снова сверяет каждый файл, текущее состояние, совместимость, простой Hub и выполняет снимок и откат.

Приватный `/var/lib/sovagrid/release-feed-state.json` хранит наибольшие принятые номер и версию выпуска, наибольшее `issued_at` проверенной ленты и время последней успешной проверки. Время сохраняется также при ответе «уже актуально»: более старая подписанная лента или откат системных часов более чем на пять минут вызывают отказ. Номер выпуска сохраняется **до** включения существующего таймера: при сбое между этими действиями требуется ручной разбор, зато не появляется разрешённого автоматического обновления без записи anti-replay. Текущее разрешение на один архив всегда имеет приоритет; лента не заменяет его. Не удаляйте ledger ради повторной попытки: используйте ручное обновление после анализа причины отказа.

## Контракт для интерфейса

Клиент с уже проверенным root SSH-сеансом может запускать один и тот же установленный скрипт без пароля, токена или хеша ленты в аргументах:

- `python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/release_feed.py status` — локальный JSON: включён ли канал, доступные идентификаторы доверенных ключей и SHA-256 их DER SPKI, установлен ли таймер, действует ли ручное разрешение на один архив, `state_revision` и anti-replay ledger. Секретов в ответе нет, сеть не используется.
- `... release_feed.py enable [key_id] --expected-state <state_revision>` — при единственном встроенном доверенном ключе проверяет **живую** подписанную ленту и совместимость с установленной версией до создания root-only конфигурации и включения таймера. При нескольких ключах клиент должен передать выбранный публичный `key_id` как аргумент. Если ключ или units отсутствуют либо состояние изменилось, команда отказывает, не включая канал. Ревизию подставляет интерфейс, пользователю её вводить не нужно.
- `... release_feed.py disable --expected-state <state_revision>` (или `disarm` без проверки ревизии) — удаляет opt-in конфигурацию и останавливает будущий поиск обновлений; anti-replay ledger сохраняется. Уже выданное отдельное разрешение на один архив не снимается молча. Если пользователь хочет отменить и его, клиент отдельно вызывает `auto_update.py disarm` после явного действия в UI.

Совместимый Connect даёт графическое включение и отключение только для точно утверждённых манифестов установленного сервера. Веб-интерфейс Hub и Web получает состояние через административный API и отправляет точную ревизию состояния при подтверждённом включении или отключении. Сервер повторно проверяет права администратора, подпись и совместимость; при неизвестном результате панель сначала обновляет состояние и не повторяет действие автоматически. Текущий веб-мастер использует единственный встроенный ключ; для будущей ротации с несколькими ключами потребуется выбор `key_id` в интерфейсе. Миграция systemd units реализована с версионированным снимком для отката. Встроенный ключ сам по себе не включает подписку: `enable` проверяет живую подписанную ленту перед записью конфигурации. Локальный часовой пояс любой страны не меняет Unix timestamps: используется UTC epoch, а не настройка зоны сервера.

## Текущий выпуск и обслуживание

1. Текущий согласованный сервер — [server-v1.0.0](https://github.com/sovagrid/sovagrid-blueprint/releases/tag/server-v1.0.0). SHA-256 архива и внутреннего `sovagrid-bundle.json` указаны в описании выпуска; контрольные суммы файлов — в [SHA256SUMS](https://github.com/sovagrid/sovagrid-blueprint/releases/download/server-v1.0.0/SHA256SUMS). Проверки состава и поддерживаемые границы собраны в [RELEASE_1_0.md](RELEASE_1_0.md).
2. [Актуальная подписанная цепочка](https://github.com/sovagrid/sovagrid-update-feed) сохраняет прежние переходы и добавляет новые с возрастающими `sequence` и версиями. Исторические переходы связывают манифесты `v0.13.0` (`f6d3b246d29661ffac4975f78dbc3a5481405b47e23826ea30a388e41f2b1280`), `v0.14.0` (`c57e46f652fcf8d3cf2ddd9e10957dedfe56e7709ccffabdd5081bb60a12e286`) и `v0.14.1` (`ec6f567b0292916dd3f104f1441451708a955b79d02ef91f82237a8cf8603f1f`). Встроенный `sovagrid-2026-10` закреплён по SHA-256 DER SPKI `abb6ed34e70fc1dd33d393987fb6067b4a69120eb3a5e00681f209e3666444bf`. Документ и подпись сверяются по этому открытому ключу; ключ из сетевой ленты не используется как источник доверия.
3. Глобальный администратор поддерживаемой установки включает подписку в Web или совместимом Connect после просмотра состояния. Сервер проверяет живую подпись и совместимость до записи конфигурации `0600` и включения таймера. Установленные `v0.13.0`/`v0.14.0` не могут включить её и исправить себя через неё: их старый updater ошибочно отклоняет ответ SSH-шлюза ещё до загрузки кандидата. Для них нужен разовый ручной переход через актуальный Connect по [инструкции](DEPLOY.md#разовый-переход-с-v0130-и-v0140). Он проверен на одноразовой Ubuntu для [`v0.13.0`](https://github.com/sovagrid/sovagrid-connect/actions/runs/41227574940) и [`v0.14.0`](https://github.com/sovagrid/sovagrid-connect/actions/runs/41227133745): намеренный сбой вызвал откат, управляемый Web Agent сохранился, а после успешной установки `v0.14.1` лента прошла `enable`/`CURRENT`/`disable`. Полная `v0.14.1` затем поддерживает подписанный переход; Hub-only `v0.14.1` сначала требует ручного перехода на новый согласованный пакет.
4. Поля `issued_at` и `expires_at` актуального [stable.json](https://github.com/sovagrid/sovagrid-update-feed/blob/main/stable.json) задаются в UTC Unix seconds. До истечения срока документ нужно продлить новой подписью; просроченная лента не разрешает обновление. Закрытый production-ключ хранится вне Git, CI и управляемых серверов; его резервную копию под контролем владельца необходимо подготовить отдельно. Будущие выпуски добавляются к подписанной цепочке с новым номером и точными хешами через [publisher](https://github.com/sovagrid/sovagrid-update-feed), без передачи ключа в CI. Подтверждённые переходы с временным ключом описаны ниже отдельно от публикации production-ленты.

Проверяющему нужен `/usr/bin/openssl` с поддержкой Ed25519. Если программы нет, проверка подписи отказывает; будущая миграция должна проверять эту зависимость до предложения включить канал.

Без включённой подписки `release_feed.py poll` отказывает с `MISSING_FILE`; при недоступной, просроченной или неправильно подписанной ленте `enable` не создаёт подписку. Локальные проверки: `python3 -m unittest tests.test_release_feed -v`, а в репозитории ленты — `python3 -m unittest discover -s tests -v`. Они используют временный Ed25519 ключ, реальные подписи OpenSSL, битые документы, недопустимые URL, `umask 077` и локальный архив; сеть и действующие серверы не нужны.

## Ограничения

Подпись доказывает владение release signing key, а не безопасность кода выпуска. Компрометация этого ключа позволяет подписать пакет с root-кодом. Смена ключа требует отдельного доверенного обновления приложения и политики отзыва; текущая версия не реализует прозрачный журнал выпусков, многостороннюю подпись или автоматический отзыв. Внешние изменения APT и побочные эффекты root-скриптов не могут быть полностью откатаны существующим worker. Автоматический путь берёт SQLite writer reservation под UID Hub, проверяет простой и останавливает контейнер Hub первым. Если новая запись успела пройти до резервирования, таймер откладывает обновление; если после, запрос ждёт освобождения SQLite или получает ошибку по таймауту. После подтверждения остановки Hub резервирование снимается, затем останавливаются остальные компоненты. При ошибке остановки оно снимается до восстановления. Ручной путь не меняется. Эта защита действует в совместимом серверном пакете; старому updater сначала требуется поддерживаемый переход. Она не заменяет режим quiescence с явным ответом клиентам 503.

## Подтверждённые переходы со старого выпуска

`tests/signed_feed_transition_vm.py ARCHIVE [full|hub_only]` выполняется только на явно
выбранной одноразовой GitHub-hosted Ubuntu. Используются временный Ed25519 ключ
и локальная модель HTTPS-ответов; подпись, архив, preflight, policy, отказ при
занятой базе и автоматическое применение выполняются настоящим кодом. В режиме
Hub-only дополнительно проверяются реальный API Hub → backup broker, arm в
transient unit с точными sandbox-директивами установленного broker unit, а также
сохранность файлов, процессов внешнего Agent и его SSH-транспортов. Production
signing key не нужен.

[Полный сценарий](https://github.com/sovagrid/sovagrid-blueprint/actions/runs/41298983265)
прошёл на установленных feed/auto/worker опубликованной `v0.14.1`: повреждённая
подпись отвергнута, занятый сервер отложил замену, согласованный кандидат применён
в простое, намеренно ошибочный кандидат откатился.
[Hub-only сценарий](https://github.com/sovagrid/sovagrid-blueprint/actions/runs/41298989964)
прошёл разовый ручной переход с `v0.14.1`, затем следующее подписанное обновление
и откат; внешний Agent и его SSH-транспорты сохранились. Эти результаты не
обозначают публикацию следующего production-выпуска или поддержку подписки
Hub-only старым пакетом `v0.14.1` без ручного перехода.

Ручной workflow `hub-only-update-vm.yml` получил выключенный по умолчанию
`signed_feed_transition` с точными `hub_ref`, `web_ref`, `agent_ref`, `vpn_ref`.
Он несовместим с отдельным destructive external-Agent trial и не добавляет
автоматических CI-запусков. Полный сценарий выбирается отдельно через
`integrated-install.yml` → `release_validation`.
