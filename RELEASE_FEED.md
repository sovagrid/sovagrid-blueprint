# Подписанный канал серверных обновлений: безопасный MVP

В `deploy/release_feed.py` реализована проверка будущих выпусков и локальный контракт `status`/`enable`/`disable` для интерфейса. Канал **не включён**: в коде нет рабочего публичного ключа и подписанной ленты, на сервере не создаётся конфигурация подписки. `run.sh` устанавливает systemd units на новой установке и при обновлении под новым worker, но оставляет таймер выключенным без явного выбора пользователя. При первом переходе со старого worker установка units откладывается до следующего контролируемого запуска `run.sh` или обновления, потому что старый worker не умеет восстанавливать их при откате. Если feed-файлы уже есть, старый worker отказывает до изменений. Существующий `sovagrid-auto-update.timer` продолжает работать только с одним заранее одобренным архивом.

На узле с собственным Hub и сохранённым внешним Agent подписанный канал полного серверного обновления не поддерживается. `enable` и `poll` отказывают с `HUB_ONLY_UNSUPPORTED` при любом признаке Hub-only promotion, включая неполный каталог или символическую ссылку, до обращения к ленте и постановки пакета. `status` остаётся доступным для диагностики, `disable` — для снятия ранее созданной подписки. Одноразовый Hub-only update использует отдельный механизм и сохраняет внешний Agent; автоматический подписанный путь для него потребуется разработать отдельно.

## Контракт канала

Источники жёстко заданы в коде:

- `https://raw.githubusercontent.com/sovagrid/sovagrid-update-feed/main/stable.json` — отдельный [публичный репозиторий ленты](https://github.com/sovagrid/sovagrid-update-feed). Он создан, но `stable.json` и подпись намеренно отсутствуют, канал неактивен. Хранить манифест в Blueprint нельзя: `package_server.py` включил бы его в архив, и SHA-256 архива рекурсивно зависел бы от самого себя. В репозитории ленты есть [publisher и проверка с временным ключом](https://github.com/sovagrid/sovagrid-update-feed), которые сами ничего не публикуют.
- тот же путь с окончанием `.sig` — ровно 64 байта отсоединённой подписи Ed25519 над **исходными байтами** JSON;
- архив `https://github.com/sovagrid/sovagrid-blueprint/releases/download/server-v<VERSION>/SovaGrid-server-source.tar.gz`. Версия строго `MAJOR.MINOR.PATCH` без ведущих нулей. Манифест не может задавать URL или команду.

GitHub описывает `browser_download_url` публичного release asset и возможность редиректа при выдаче архива в [документации Release assets](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28). Перед вводом канала нужно проверить настоящий выпуск end-to-end: этот MVP тестировался без сети, а GitHub может изменить CDN-домен. В этом случае загрузка остановится до review и обновления allowlist.

Проверяющий не передаёт учётные данные, не использует переменные прокси, требует TLS и принимает редиректы только на `github.com`, `release-assets.githubusercontent.com` и `objects.githubusercontent.com`. CDN может добавлять временный query-параметр; он не используется как вход для выполнения команд. Нет поддержки произвольного зеркала, приватного GitHub-релиза или GitHub API с токеном.

Схема подписанного документа:

```json
{
  "format": 1,
  "channel": "stable",
  "key_id": "REVIEWED_KEY_ID",
  "issued_at": 1800000000,
  "expires_at": 1800600000,
  "releases": [
    {
      "sequence": 1,
      "version": "0.3.10",
      "from_manifest_sha256": "64 lowercase hex characters",
      "to_manifest_sha256": "64 lowercase hex characters",
      "archive_sha256": "64 lowercase hex characters",
      "archive_size": 12345678
    }
  ]
}
```

Это иллюстрация полей, не публикуемый манифест. Выпуски идут строго по возрастающим `sequence` и версии; `to_manifest_sha256` одной записи совпадает с `from_manifest_sha256` следующей. Можно оставить в ленте цепочку до 32 выпусков, чтобы отстающий сервер проходил их по одному. `issued_at` и `expires_at` — Unix seconds в UTC, независимо от страны и часового пояса сервера. Другая страна не объясняет расхождение UTC-часов на 165 секунд: это отдельный вопрос синхронизации. Время сервера должно быть достаточно точным: откат более чем на пять минут или просроченный манифест вызывает отказ. Подписанный документ действует максимум 30 дней и требует повторной подписи при продлении.

Проверяющий отвергает неизвестные поля, дубликаты JSON-ключей, некорректную версию, неподходящий исходный манифест и повтор старого `sequence`/версии. Он ограничивает размер ленты 32 КБ, архива 64 МиБ, распаковки 256 МиБ и число элементов 4096. SHA-256 архива и манифеста новой версии сверяются **до** передачи кандидата действующему `auto_update.py`. Из архива принимаются только обычные файлы и каталоги с безопасными именами и правами. Затем существующий transaction worker снова сверяет каждый файл, текущее состояние, совместимость, простой Hub и выполняет снимок и откат.

Приватный `/var/lib/sovagrid/release-feed-state.json` хранит наибольшие принятые номер и версию выпуска, наибольшее `issued_at` проверенной ленты и время последней успешной проверки. Время сохраняется также при ответе «уже актуально»: более старая подписанная лента или откат системных часов более чем на пять минут вызывают отказ. Номер выпуска сохраняется **до** включения существующего таймера: при сбое между этими действиями требуется ручной разбор, зато не появляется разрешённого автоматического обновления без записи anti-replay. Текущее разрешение на один архив всегда имеет приоритет; лента не заменяет его. Не удаляйте ledger ради повторной попытки: используйте ручное обновление после анализа причины отказа.

## Контракт для интерфейса

Клиент с уже проверенным root SSH-сеансом может запускать один и тот же установленный скрипт без пароля, токена или хеша ленты в аргументах:

- `python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/release_feed.py status` — локальный JSON: включён ли канал, доступные идентификаторы доверенных ключей и SHA-256 их DER SPKI, установлен ли таймер, действует ли ручное разрешение на один архив и anti-replay ledger. Секретов в ответе нет, сеть не используется.
- `... release_feed.py enable` — при единственном встроенном доверенном ключе проверяет **живую** подписанную ленту и совместимость с установленной версией до создания root-only конфигурации и включения таймера. При нескольких ключах UI передаёт выбранный публичный `key_id` как второй аргумент. Если ключ или units отсутствуют, команда отказывает, не включая канал.
- `... release_feed.py disable` (или `disarm`) — удаляет opt-in конфигурацию и останавливает будущий поиск обновлений; anti-replay ledger сохраняется. Уже выданное отдельное разрешение на один архив не снимается молча. Если пользователь хочет отменить и его, клиент отдельно вызывает `auto_update.py disarm` после явного действия в UI.

Это готовый серверный контракт, а не готовая кнопка: Connect/веб-интерфейс должны подключить его отдельно. Миграция systemd units реализована с версионированным снимком для отката. Пока `TRUST_ANCHORS` пуст, `enable` заведомо отказывает, даже если units установлены. Локальный часовой пояс любой страны не меняет Unix timestamps: используется UTC epoch, а не настройка зоны сервера.

## Что требуется для ввода в эксплуатацию

1. Организовать доверенное создание и хранение production signing key **вне** серверов, CI-логов и репозиториев. Согласовать владельцев и процедуру независимой сверки публичного ключа и его fingerprint. Приватный ключ не создавался для этого MVP; в тестах он временный и удаляется после запуска. Пустой репозиторий метаданных уже создан без ключей и активного feed.
2. Добавить проверенный сырой 32-байтовый публичный Ed25519 ключ в `TRUST_ANCHORS`, выполнить review, выпустить код обычным контролируемым обновлением и проверить независимым клиентом fingerprint установленного кода. Нельзя подставлять ключ из самой сетевой ленты: это отменит проверку происхождения.
3. Создать **новый stable release** с указанным именем и тегом; текущие preview-теги не подходят и не изменяются. [Publisher](https://github.com/sovagrid/sovagrid-update-feed) скачает уже опубликованный архив, выведет размер/SHA-256 и SHA-256 внутреннего `sovagrid-bundle.json`, затем повторно скачает его перед подписью и сравнит с независимо утверждённым SHA-256. Нужно указать точный SHA-256 исходного установленного манифеста. Подписать окончательные байты `stable.json` вне сервера и проверить архив с двумя участниками или равноценным контролируемым выпуском: подписанный пакет содержит `run.sh`, который updater исполняет от root. Приватный ключ не передаётся в CI.
4. Подключить графическое включение и отключение на каждом сервере через проверенный root/sudo SSH-сеанс: UI вызывает `status`/`enable`/`disable`, запись конфигурации `0600` выполняет сам серверный скрипт. Установка units в `run.sh` уже подготовлена, но при переходе со старого worker сознательно откладывается до запуска под новой версией worker с полным снимком для отката. Пользователю не потребуется вводить хеши и токены в консоль.

Проверяющему нужен `/usr/bin/openssl` с поддержкой Ed25519. Если программы нет, проверка подписи отказывает; будущая миграция должна проверять эту зависимость до предложения включить канал.

До завершения этих шагов `release_feed.py poll` обязан отказать с `UNCONFIGURED_TRUST` или `MISSING_FILE`, а `enable` — с `UNCONFIGURED_TRUST`. Проверки: `python3 -m unittest tests.test_release_feed -v`, а в репозитории ленты — `python3 -m unittest discover -s tests -v`. Они используют временный Ed25519 ключ, реальные подписи OpenSSL, битые документы, недопустимые URL, `umask 077` и локальный архив; сеть и действующие серверы не нужны.

## Ограничения

Подпись доказывает владение release signing key, а не безопасность кода выпуска. Компрометация этого ключа позволяет подписать пакет с root-кодом. Смена ключа требует отдельного доверенного обновления приложения и политики отзыва; текущий MVP не реализует прозрачный журнал выпусков, многостороннюю подпись или автоматический отзыв. Внешние изменения APT и побочные эффекты root-скриптов не могут быть полностью откатаны существующим worker. В исходниках автоматический путь теперь берёт SQLite writer reservation под UID Hub, проверяет простой и останавливает контейнер Hub первым. Если новая запись успела пройти до резервирования, таймер откладывает обновление; если после, запрос ждёт освобождения SQLite или получает ошибку по таймауту. После подтверждения остановки Hub резервирование снимается, затем останавливаются остальные компоненты. При ошибке остановки оно снимается до восстановления. Ручной путь не меняется. Эта защита начнёт действовать на узлах только после установки соответствующего серверного пакета. Она не заменяет режим quiescence с явным ответом клиентам 503.
