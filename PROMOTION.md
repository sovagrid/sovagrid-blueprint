# Отдельный Hub на сервере с Agent

Если на Ubuntu уже работает SovaGrid Agent, подключённый к другому Hub, мастер Connect «Свой Hub на сервере с Agent…» может установить на том же узле независимый локальный Hub и второй Agent. Перед установкой нужен root SSH либо пользователь с `sudo -n` и проверенный серверный пакет. Этот режим предназначен для любого своего сервера, включая узлы, доступные через промежуточный SSH-хост.

## Порядок установки

1. В Connect выберите профиль целевого Ubuntu-сервера и проверьте отпечатки SSH-хостов на маршруте.
2. Откройте мастер «Свой Hub на сервере с Agent…» и укажите доверенный `SovaGrid-server-source.tar.gz`.
3. Дождитесь чтения `inspect`: мастер проверит исходный Agent, его enrollment, конфигурацию и транспорт по контрольным суммам, а также текущую версию пакета.
4. Подтвердите план. Мастер выполнит `prepare`, установит Hub через `run.sh --hub-only` и выполнит `activate` для второго локального Agent.
5. После установки подключитесь к панели локального Hub через SSH-профиль целевого сервера. Другой Hub и исходный Agent продолжают работать независимо.

`prepare` сохраняет приватный контрольный снимок исходного Agent и работающих обратных SSH-туннелей на целевом сервере. `activate` сверяет снимок перед изменениями. Дополнительные reverse SSH units обнаруживаются по их локальным systemd `ExecStart` с `ssh -R`/`autossh -R`; имя конкретной службы в пакет не встроено. Снимок хранит только контрольные суммы и режимы файлов, не содержимое ключей или токенов.

## Функции локального Agent

После активации можно через Connect включить команды, PTY, рабочую папку и просмотр Docker для второго Agent. Эти функции управляются отдельно от исходного Agent. Для терминала создаётся отдельный непривилегированный пользователь; полномочия исходного Agent и его SSH-учётные данные не копируются. Включение и выключение выполняются через мастер «Включить функции…» с предварительным просмотром и повторной проверкой состояния.

## Обновление

Для локального Hub используется отдельное Hub-only обновление. Подготовленный архив и манифест текущей версии закрепляются однократной root-only политикой; таймер не загружает новые версии самостоятельно и не включается без политики. Если Agent занят, обновление откладывается. При ошибке пакет откатывается или мастер показывает состояние, требующее внимания.

Обновление **исходного внешнего Agent** остаётся отдельной операцией. `deploy/external_agent_update.py preview` только проверяет кандидат и совместимость с исходным Hub; текущий публичный интерфейс возвращает `apply_supported=false`. Транзакционный примитив и восстановление после прерывания реализованы в `deploy/external_agent_recovery.py`, но запуск обновления требует дополнительного координирующего кода и подтверждённого простоя исходного Agent.

Сценарий развёртывания и сохранности исходных служб проверяется на одноразовых Ubuntu VM в CI. Для любого конкретного сервера перед применением повторите `inspect`, сохраните резервную копию и проверьте результат через панель.
