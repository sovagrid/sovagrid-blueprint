# Резервная копия управляемого состояния Ubuntu-хоста

`deploy/host_backup.py` — низкоуровневая root-only операция для полного **управляемого состояния SovaGrid** на одном хосте. Она дополняет снимки отдельной базы Hub в `/var/lib/sovagrid/backups`. Архив хоста содержит состояние Hub вместе с уже созданными снимками Hub, конфигурацию, ключи и сертификаты SovaGrid, политику broker, файлы systemd, необязательный marker управляемого SSH gateway и проверенный установленный `/opt/sovagrid-src`. Он хранится отдельно в `/var/lib/sovagrid-host-backups`, чтобы никогда не попасть в собственный обход.

Архив содержит секреты. Каталог имеет владельца `root:root` и режим `0700`; `.tar.gz` и `.manifest.json` имеют `root:root 0600`. JSON-ответ CLI показывает только идентификатор, время UTC, схему хоста, размер и число записей. Манифест содержит SHA-256 архива и digest установленного source manifest, без списка имён и содержимого секретов. Обычный архив не имеет HTTP/API для скачивания; отдельная переносимая операция доступна в Web после проверки и одноразовой авторизации.

**Текущий статус:** [server-v1.0.0](https://github.com/sovagrid/sovagrid-blueprint/releases/tag/server-v1.0.0) включает квитанцию v2, подготовку зависимостей, клиентские мастера, независимый исполнитель и полную транзакцию применения/восстановления. `APPLY_ENABLED=True`: [общий Ubuntu-прогон](https://github.com/sovagrid/sovagrid-blueprint/actions/runs/41332122229) проверил откат после гибели процесса, полноценный запуск с переподключением во время активного публичного worker и сохранение изменившейся SQLite после ошибки здоровья. Доступность конкретной операции определяется capability проверенного исполнителя, готовностью цели и свежим подтверждённым планом. Состав и границы выпуска — в [RELEASE_1_0.md](RELEASE_1_0.md).

## Граница схем

| Схема | Включено | Исключено |
|---|---|---|
| Full Hub+Agent | База Hub, снимки Hub и их root-only журналы, Caddy CA и ключи, пароль первого администратора, Agent config/token и его локальный код, управляемые WireGuard state/client keys, локальная политика Amnezia, VPN, service, routing и journal broker, точные unit-файлы | `/root/.ssh`, `/home`, пользовательские файлы Agent `/var/lib/sovagrid-agent/files`, SSH-транспорты внешних Agent и ключи SSH самого Ubuntu, сторонние Docker volumes, чужие VPN и systemd-службы |
| Hub-only + внешний Agent | База и снимки локального Hub, его Caddy CA, пароль администратора, локальный Agent config/token и код, локальные политики, точные unit-файлы, установленный source bundle | Конфиг, токен, CA, код, данные и SSH-туннель внешнего Agent; его WireGuard/Amnezia state и ключи; `/var/lib/sovagrid-agent-local/files` |

**Внешние Agent после переноса.** База Hub сохраняет строки удалённых серверов, но архив не переносит состояние `/var/lib/sovagrid-hub-tunnels`, соответствующие SSH policy/authorized keys и учётные записи `sgt_*`. Системные ключи SSH самого Ubuntu также исключены. После восстановления Hub такие SSH-подключения нужно заново подготовить через Connect или Web-мастер; наличие старой строки сервера не означает работающий транспорт. Эти данные не удаляются с исходного пользовательского сервера операцией создания копии.

Если на Hub-only узле включён локальный сбор контейнеров, архив дополнительно содержит его root-owned состояние, точные два systemd unit и очищенный снимок `/var/lib/sovagrid-containers-local/snapshot.json`. Это только локальные данные; инвентарь внешнего Agent не копируется. Незавершённое включение или выключение коллектора блокирует создание архива до `recover`.

На обеих схемах установленный Web Agent входит в архив вместе с точными `sovagrid-web-agent-control.socket` и `.service`, root-owned marker `/var/lib/sovagrid/.web-agent-installer-managed-by-run-sh` и закрытым каталогом `/var/lib/sovagrid/web-agent`. Последний включает версионированные `source-<sha256>.tar.gz`, `jobs/<request-id>.json`, файлы блокировок и, если создан, `completed-enrollments.jsonl`. Каталоги должны быть `root:root 0700`, файлы — `root:root 0600`; каждый bundle сверяется с SHA-256 в имени. Неизвестные файлы, неверные режимы и частично установленное состояние блокируют архив. Безопасные остатки прерванной атомарной записи `.source-*` и `.enrollment-*` не включаются. Незавершённые установки удалённых Agent сохраняют локальный журнал для последующего возобновления, но состояние самого удалённого хоста остаётся вне этого архива.

Установленный `/opt/sovagrid-src` включается только если `source_manifest(..., allow_generated=True)` подтвердил весь release bundle. Дополнительный файл, symlink или несовпадающий hash прерывает операцию. Для хранилищ и конфигурации проверяются точные владельцы, режимы и отсутствие symlink, hardlink, сокетов, устройств и групповой/общей записи. Для `hub.sqlite`, bootstrap-пароля, Bot token и Hub-only политики проверяются особые режимы. Некоторый код и публичные сертификаты читаемы на хосте, но закрытый Caddy root защищён каталогом `0700`; весь выходной архив закрыт `0600`.

## Контракт для Connect

Исполнять только через проверенное root SSH-подключение и из root-owned установленного bundle:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py plan
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py source
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py create
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py list
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py verify <32-hex-id>
```

Успех — exit `0` и ровно одна строка JSON с `ok:true`, `protocol:"sovagrid-host-backup-v1"`. `plan` возвращает `layout`, `active_units` (точный перечень активных локальных writer units), `running_containers` (`[]`, `hub`/`web` или `hub`/`web`/`ssh-gateway`) и `offline_ready`. Gateway — необязательная третья служба: установки 0.6 без него остаются допустимы. Работающий gateway признаётся управляемым только при точном root:root `0600` marker `/var/lib/sovagrid/.ssh-gateway-managed-by-run-sh`; отсутствующий или повреждённый marker блокирует операцию. Запущенный Web Agent тоже требует точный root:root `0600` marker; его socket и service включены в локальные writer units. `source` возвращает digest установленного source manifest для проверки поколения перед запуском. `create` возвращает `archive` с `id`, `created_at` (ISO 8601 UTC), `layout`, `bytes`, `files`. `list` возвращает `archives`, в том числе пустой массив до первого создания, отсортированный по времени от новых к старым. `verify` возвращает те же поля `archive` и `verified:true`. Отказ — exit `40`, одна строка `{"ok":false,"protocol":"sovagrid-host-backup-v1","error":"CODE"}`. Основные коды: `ROOT_REQUIRED`, `BUSY`, `SERVICES_RUNNING`, `CONTAINERS_RUNNING`, `UNMANAGED_GATEWAY`, `UNSAFE_GATEWAY_MARKER`, `UNMANAGED_WEB_AGENT`, `UNSAFE_WEB_AGENT_MARKER`, `UNMANAGED_UNIT`, `UNKNOWN_ACTIVE_UNIT`, `CONTAINER_AMBIGUOUS`, `SOURCE_UNAVAILABLE`, `SOURCE_UNSAFE`, `UNSAFE_SOURCE`, `MISSING_SOURCE`, `SOURCE_CHANGED`, `DISK_SPACE`, `SIZE_LIMIT`, `FILE_LIMIT`, `TIME_LIMIT`, `NOT_FOUND`.

`plan` только читает состояние; его результат может устареть. `create` вновь проверяет схему, source manifest и активность служб после получения общих locks. На Hub-only узле первым берётся `/run/sovagrid-promotion.lock`, чтобы локальный коллектор не менялся во время архивации; затем следуют `/opt/sovagrid-candidates/.lock` и `/var/lib/sovagrid/.public-web.lock`. Работающий внешний Agent и обратный SSH-туннель внешнего Agent, а также `sovagrid-vpn-routing.service` не входят в набор локальных writer units и не останавливаются. SovaGrid Agent остаётся активным даже на Full-узле: в архив включены его статические конфигурации, а изменение установленного bundle блокируется общим lock и дополнительно обнаруживается повторной сверкой файлов. На Hub-only узле внешние Agent и туннель не участвуют в снимке.

Для согласованности низкоуровневый `create` требует остановленных Hub/Web/SSH gateway контейнеров и локальных writer timers/brokers из `plan`. Скрипт сам не меняет службы. Графический клиент пользуется отдельным root-only `host_backup_orchestrator.py`: он ведёт долговечный журнал запроса, запускает операцию под transient systemd unit, останавливает только перечень из повторно проверенного плана, вызывает `_create_locked()` с заранее записанным ID архива и снова запускает ранее работавшие контейнеры и units. Таймер после включения может кратко активировать собственную одноразовую службу; это не считается потерей исходного состояния. Внешний Agent, обратный туннель внешнего Agent и VPN routing не останавливаются. Если изначально запущен неполный состав Hub/Web, с gateway или без него, либо работает одноразовый writer service, операция отказывается до простоя. Неизвестные контейнеры с Compose project label `sovagrid` тоже блокируют операцию.

Контракт графического клиента после подтверждения:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py start <32-hex-request-id> <64-hex-installed-source-manifest>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py status <32-hex-request-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py list
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py recover <32-hex-request-id>
```

Ответ записи операции: `ok`, `protocol:"sovagrid-host-backup-operation-v1"`, `request_id`, `phase`, `archive` (либо `null`), `error` (либо `null`), `created_at` в UTC. `list` возвращает до 100 таких записей в `operations`. `start` с тем же UUID лишь читает журнал и никогда не повторяет создание. После потерянного SSH-ответа клиент читает `status` или `list`. Фазы `complete`, `recovered`, `failed` терминальны; `recovery_required` указывает на отдельное `recover`, которое **только** восстанавливает службы, а не повторяет архив. При аварийном прерывании архив определяется по заранее записанному ID, а удаляться могут только его неполные временные файлы. Если исходники, unit-файлы или container ID изменились, автоматическое восстановление откажется, сохраняя журнал для разбора. Для gateway проверяется его Compose service label, прежний container ID и Docker healthcheck; gateway с новым ID не подменит остановленный экземпляр. Готовый архив всё ещё можно читать только от root на самом сервере.

У root CLI есть отдельный режим start-portable с UUID запроса и SHA-256 установленного манифеста, а также portable-status с тем же UUID. Он требует работающие управляемые Hub/Web и необязательный gateway, закрепляет исходные container/image ID и SHA-256 вектора RootFS слоёв каждого точного локального тега, создаёт архив, восстанавливает и проверяет службы, затем под теми же блокировками экспортирует образы. Исходные container/image ID, теги и RootFS сверяются после экспорта. Затем он атомарно публикует закрытый `receipt.json` внутри каталога образов и только после этого записывает `complete` в журнал. Квитанция содержит SHA-256 обоих артефактов, исходного кода, unit/container/image ID, RootFS и отдельно digest экспортированной конфигурации; она переносится вместе с образом на чистый хост без исходного журнала. В новых исходниках `start-portable` создаёт квитанцию `sovagrid-portable-host-receipt-v2`: поле `unit_states` связывает каждый присутствующий точный управляемый systemd unit (из перечня до 24 для Full и до 20 для Hub-only) с `active` (булево), строкой `enablement` из ограниченного списка состояний systemd и SHA-256 его файла. Запись состояния до остановки служб и повторная сверка не дают подменить даже неактивный unit; v2 сверяется с байтами unit-файлов внутри основного архива. Ошибка экспорта или публикации квитанции даёт `failed/IMAGES_FAILED`, сохраняя основной архив для отдельной проверки; recover не повторяет экспорт и не выдаёт `complete`. Перед переносом root повторяет `verify` архива и `verify-portable` образов. Старые start/status и ответы Connect не меняются; в Web есть отдельная кнопка создания переносимой копии.

## Доступ из веб-панели

Полный администратор локального Hub видит в настройках план остановки, список закрытых архивов и операций, проверку целостности, запуск и восстановление служб. Hub передаёт root broker только фиксированные действия и идентификаторы. Обычный архив не выдаётся по HTTP. Для переносимой операции Web дополнительно вызывает root-проверку и выдаёт короткое одноразовое разрешение на скачивание выбранного файла в том же сеансе и origin Hub; архив содержит секреты. Запуск и `recover` записываются в аудит. Браузер сохраняет UUID запроса до POST, чтобы после временной остановки Hub/Web проверить ту же операцию без повторного создания. Если Hub не вернулся, Web не может выполнить `recover`; используйте Connect по SSH с тем же UUID. Каталог журнала `/var/lib/sovagrid-host-backup-operations` создаёт установщик с `root:root 0700` до запуска broker.

Лимиты: 20 000 записей, 8 GiB суммарного содержимого и готового архива, 4 GiB на один файл, 300 секунд на source check/обход/запись, 60 секунд на проверку release source, минимум 256 MiB запаса диска сверх несжатого размера, максимум 100 архивов. При отказе временные файлы и частично опубликованный архив удаляются. `verify` проверяет SHA-256 готового архива и структуру tar; сам этот режим не меняет рабочие пути. Применение переносимой копии выполняет отдельный исполнитель с проверкой capability и подтверждённого плана. Gateway не имеет отдельного persistent volume; Docker images Hub/Web/Gateway не входят в основной архив. Для них есть отдельный закрытый экспорт ниже. Архив представляет состояние SovaGrid, а не образ всего диска Ubuntu.

## Отдельный экспорт Docker-образов

После успешного архива и перезапуска контейнеров root может выполнить:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py create <32-hex-host-archive-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py verify <32-hex-host-archive-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py verify-portable <32-hex-host-archive-id>
```

`create` под общими locks обновления заново проверяет основной host archive и его установленный source digest. Затем он требует полный работающий Compose stack (`hub`, `web` и, если есть проверенный marker, `ssh-gateway`), сверяет для каждого сервиса image ID работающего контейнера с точным тегом `sovagrid-<service>:local`, берёт у тега упорядоченный `RootFS.Layers` и повторяет обе проверки после экспорта. `docker image save` получает только эти точные теги; image config и слои проверяются по SHA-256, а чужие теги, лишние tar-файлы и неподдерживаемые платформы отклоняются. В Docker с containerd ID образа может обозначать manifest или index, поэтому он не обязан совпадать с digest конфигурации. Манифест раздельно сохраняет исходный ID и config digest. Проверка связывает ID с криптографически проверенным графом config/manifest/index данного сервиса, сверяет точные теги, платформу и исходный/экспортированный векторы `RootFS.Layers`/`rootfs.diff_ids`. Одного совпадения слоёв для этой привязки недостаточно. Если версия исходников, состав/ID контейнеров, теги или RootFS изменились, операция отказывает и удаляет своё временное дерево. Экспорт не останавливает службы.

Артефакт публикуется одним rename в `/var/lib/sovagrid-host-image-exports/<id>/`: `images.tar` и `manifest.json` внутри имеют `root:root 0600`, каталоги — `root:root 0700`. Режим `start-portable` дополнительно атомарно добавляет `receipt.json` с теми же правами. Манифест связывает экспорт с ID, SHA-256 и source digest основного архива и содержит точные исходные image/container IDs, `exported_configs`, `rootfs_sha256`, размер, число tar-записей, SHA-256 образов и время UTC. Для переноса нужны все три файла каталога экспорта, а также `<id>.tar.gz` и `<id>.manifest.json` из `/var/lib/sovagrid-host-backups`; права root и режимы необходимо сохранить. Web выдаёт все пять файлов отдельными одноразовыми загрузками с точными именами. На целевом хосте разместите `<id>.tar.gz` и `<id>.manifest.json` в `/var/lib/sovagrid-host-backups/`, а `images.tar`, `manifest.json` и `receipt.json` — в `/var/lib/sovagrid-host-image-exports/<id>/`; затем запустите проверку и предпросмотр восстановления. Лимиты: 8 GiB для потока Docker и суммарной распаковки gzip-слоёв при проверке, 20 000 tar-записей, 1200 секунд, не менее 256 MiB свободного места после очередного блока записи, 8 KiB на квитанцию. Уже опубликованный ID не перезаписывается. При обычном отказе удаляется только свой временный каталог; после аварийного завершения скрытый временный каталог остаётся для ручного разбора root.

`verify` работает и на чистом Ubuntu-хосте без Docker daemon. Он заново проверяет основной архив, закрытые метаданные и SHA-256 полного `images.tar`, все пути и типы внешнего Docker tar, его `manifest.json`, SHA-256 каждого image config и `rootfs.diff_ids` каждого объявленного layer. Поддерживаются legacy Docker tar и проверенный вариант OCI tar, который создаёт Docker на Ubuntu: каждый blob сверяется с digest/size OCI descriptor, gzip-слои ограниченно распаковываются для проверки diff ID, чужие теги и неперечисленные файлы запрещены. `verify-portable` дополнительно требует квитанцию, сверяет её поля с обоими артефактами и выдаёт исходные active units, container/image IDs и проверенную платформу каждого образа в `platforms`; ему не нужен журнал исходного сервера. Это проверка сохранённых байтов, а не доказательство происхождения копии: перед переносом следует удостоверить источник пары по защищённому каналу. Каталог экспорта исключён из проверки занятости `clean-plan`, поскольку это входные данные для восстановления. Команды экспорта и проверки сами не выполняют `docker load`, переключение тегов, установку файлов или запуск контейнеров. Эти действия относятся к отдельной транзакции применения и разрешаются только готовым исполнителем после подтверждения. Основной архив сам по себе по-прежнему выдаёт блокер `DOCKER_IMAGES_NOT_INCLUDED`. Панель может запустить `start-portable` и проверить результат. Для уже существующего обычного архива отдельный экспорт образов вызывается root-only командой после завершения архивации.

## Проверка и подготовка восстановления на чистом хосте

Восстановление использует **пять связанных файлов**: `<id>.tar.gz` и `<id>.manifest.json` в `/var/lib/sovagrid-host-backups/`, а также `images.tar`, `manifest.json` и `receipt.json` в `/var/lib/sovagrid-host-image-exports/<id>/`. ID — 32 строчных hex-символа. На целевом хосте файлы имеют `root:root 0600`, каталоги — `root:root 0700`; symlink и hardlink запрещены. Connect и Web доставляют и регистрируют эти файлы автоматически; ручная раскладка нужна только для низкоуровневого CLI.

Проверяющий и восстанавливающий код берётся из **независимо проверенного закреплённого релиза**, а не из выбранной копии. SHA-256 внутри копии подтверждает согласованность байтов, но не её происхождение. Архив содержит секреты и установленный исполняемый код: после применения этот код может работать с правами root. Выбирайте собственную доверенную копию. Независимый runner остаётся в `/root/.sovagrid-restore/<operation_id>/runner`, поэтому публикация восстановленного `/opt/sovagrid-src` не подменяет механизм восстановления.

Низкоуровневые команды запускаются от root через `python3 -I` из этого проверенного дерева:

| Команда `deploy/host_restore.py` | Назначение |
| --- | --- |
| `clean-plan <id>` | Проверить архив хоста, пути, NSS и чистоту цели; без Docker-экспорта сохраняется блокер `DOCKER_IMAGES_NOT_INCLUDED` |
| `stage <id>` / `stage-status <id>` | Создать / повторно проверить закрытую стадию архива без записи в рабочие пути |
| `portable-clean-plan <id>` | Проверить все пять файлов, Docker/platform, ресурсы, порты и место; получить `review_sha256` |
| `portable-stage <id> <review_sha256>` | Подготовить закрытую стадию, связав её со свежим планом и экспортом |
| `portable-stage-status <id>` | Повторно проверить стадию и неизменность исходной переносимой копии |
| `portable-apply-preview <id>` | Получить capability, готовность, блокеры и окончательный `apply_review_sha256` |
| `portable-apply <id> <apply_review_sha256>` | При доступной capability применить только подтверждённый план |
| `portable-apply-status <id>` | Прочитать долговечный журнал без повторного запуска применения |
| `portable-apply-recover <id>` | Явно восстановить только ресурсы незавершённой операции |
| `portable-apply-retry <id> <terminal_sha256>` | После полного отката сохранить историю и подготовить новую попытку с новым планом |

`clean-plan` сверяет hash сжатого архива, каждый tar-путь, тип, UID/GID и режим, обязательные закрытые данные, встроенный `sovagrid-bundle.json` и исходники. Он не распаковывает файлы. Через системный NSS проверяются обязательные имена и числовые UID/GID, группа Web Agent и архивный ненулевой GID Agent; конфликт блокирует цель. Ответ содержит счётчики и фиксированные коды без имён и содержимого секретных файлов. Занятый путь, symlink или доступный посторонним для записи родитель также закрывают план. Входные каталоги самой копии исключаются из проверки пустоты.

`stage` повторно проверяет архив из удерживаемого FD и атомарно публикует `/var/lib/.sovagrid-host-restore-staging/<id>`. В закрытой стадии каталоги имеют `root:root 0700`, файлы — `root:root 0600`; исходные владельцы и режимы остаются в tar и отдельно используются при применении. Ожидаемый digest дерева вычисляется из проверенного архива, включая неявных родителей, до публикации. `stage-status` обнаруживает изменённые и посторонние файлы. Стадия с тем же ID не перезаписывается (`STAGE_EXISTS`); неопубликованный временный каталог после аварии не признаётся завершённой стадией. Обычная стадия не создаёт пользователей, не запускает службы и не пишет в живые `/etc`, `/opt`, `/usr/local` и рабочие `/var/lib/sovagrid*`.

`portable-clean-plan` добавляет проверку образов и квитанции, архитектуры, зависимостей, Docker-ресурсов и TCP-портов 80, 443, 8766, 8767. UDP-порты поддерживаемых WireGuard-инстансов извлекаются из ограниченного `state.json` и сверяются с `server.conf`. Неоднозначная VPN-конфигурация даёт `VPN_PORT_UNVERIFIED`. Учитываются старый и новый форматы Docker Compose. План возвращает счётчики конфликтов и `review_sha256`; готовность — снимок состояния, который повторно проверяется перед мутациями.

`portable-stage` принимает только свежий digest и отсутствие физических блокеров; выключенная capability применения сама по себе не запрещает подготовку. Все входные метаданные удерживаются через закрытые FD под lock и повторно сверяются. Квитанция стадии связывает план, архив, source digest, Docker tar, точные байты image manifest/receipt и digest дерева. Образы остаются во входном каталоге и не копируются второй раз. Прерывание между стадией и её переносимой квитанцией допускает проверенный повтор подготовки. Квитанция v1 пригодна для проверки и стадии, но полное применение требует v2 со всеми состояниями systemd unit.

План учитывает место копии, распаковки, рабочих данных и **дополнительные 8 ГиБ** для ограниченного повторного экспорта образов при смене Docker storage format. Это запас свободного места, а не заранее созданный файл на 8 ГиБ. Временный экспорт ограничен по размеру/времени и существует как анонимный приватный файл на файловой системе стадии. Для небольшой установки рекомендуется диск цели от 20 ГиБ; решают фактические значения «свободно» и «требуется» для выбранной копии.

### Зависимости, транспорт и возможность применения

Закреплённый bootstrap запускает `run.sh --restore-dependencies-only --expected-source-manifest-sha256 <sha256>` под ранним installation lock. Режим проверяет source pin и чистоту Ubuntu 22.04/24.04/26.04 с systemd до и после установки недостающих Python, Docker/Compose, `iproute2`, `wireguard-tools`, `python3-cryptography` и `nftables`. Если Python сначала отсутствует, проверяемый Python-код не импортируется до итоговой сверки. Подготовка не создаёт SovaGrid-аккаунтов, секретов, unit-файлов, контейнеров или живой установки. Зависимости и повторный bootstrap с двоичной передачей уже проверялись на одноразовой Ubuntu; это не заменяет проверку полной транзакции.

[Протокол целевого сервера](deploy/PORTABLE_RESTORE_TARGET.md) использует одно аутентифицированное SSH-соединение и порции до 4 МиБ. Регистрация повторно проверяет пять файлов до публикации фиксированных входных имён. Совпадающий незавершённый фрагмент можно продолжить; чужой файл не усыновляется даже при одинаковых байтах. Учётные данные не сохраняются в журнале операции.

В Web и Connect уже реализованы выбор копии, доверие SSH-ключам, bootstrap, передача, план, подтверждение, история и повторное подключение. В Web внутренние шесть полей политики полного v2-плана строго проверяются и преобразуются в четыре публичных поля без изменения review SHA. UI не включает capability сервера самостоятельно.

`portable-apply-preview` повторно проверяет стадию и ресурсный план. `backend_supported` сообщает возможность конкретного runner, `target_ready` — отсутствие физических блокеров, `apply_available` разрешает подтверждение только при обоих условиях. Окончательный `apply_review_sha256` связывает хеши всех входов, стадии, ресурсов, политику, capability и ревизию попытки. Изменение любого условия требует нового просмотра. При выключенной capability применение возвращает `APPLY_NOT_IMPLEMENTED`; это имя совместимого кода отказа, а не отсутствие транзакции в исходниках. `status` и явное восстановление незавершённой операции не требуют включения нового forward apply.

### Транзакция, журнал и восстановление

`portable_restore_apply.py`, `portable_restore_shadow.py`, `portable_restore_compose.py`, `portable_restore_runtime.py` и `portable_restore_queue.py` реализуют транзакцию. Она удерживает все пять проверенных FD и locks в порядке `installation → staging → image-export`, повторяет подтверждённый план и сохраняет закрытые bindings входов и ресурсов. Каждый внешний шаг получает синхронизированный intent до действия; состояния шага — `pending`, `intent`, `done`, `reverting`, `reverted`. Журнал записывается через `0600` temporary, `fsync(file)`, atomic rename и `fsync(directory)`. Фазы: `prepared → applying → healthy → committed`; возврат идёт через `rolling_back → rolled_back` либо `recovery_required`.

После синхронизации журнала публикуется постоянный `/var/lib/.sovagrid-host-restore-in-progress`, привязанный к ID и digest операции. Обычная установка, обновление и новый bootstrap отказывают при чужом незавершённом восстановлении. Fence переживает смерть процесса и reboot и снимается только после синхронизированного `committed` или полного `rolled_back`. Дополнительно проверяются прочие незавершённые журналы; ручное удаление fence не разрешает новую операцию.

Ресурсы ограничены проверенными архивными записями под `/etc/sovagrid*`, `/var/lib/sovagrid*`, `/opt/sovagrid-*` и точными leaf-файлами в `/etc/systemd/system`, `/etc/sysctl.d`, `/usr/local/bin` и `/usr/local/libexec`. Shadow-деревья создаются после intent на файловой системе адресата с nonce-маркером владения. Публикация использует `renameat2(RENAME_NOREPLACE)` относительно удерживаемого родительского FD; пути архива не передаются shell. Владельцы и режимы живых файлов выводятся из проверенного tar и правил установщика, а не из закрытых режимов стадии. Неявные родители, пустые каталоги Agent/терминала, backup broker и Unix-сокетов имеют отдельные правила. Созданный родитель удаляется при откате только пустым и при доказанном владении.

Фиксированные системные identities сверяются с контрактом; Hub использует UID/GID `10001:10001`, Web Agent socket — группу `sovagrid-web-agent` GID `10005`. Agent получает свободный ненулевой системный UID и архивный GID. Существующие NSS-записи не усыновляются. Перед откатом проверяются имена, числовые IDs, home/shell и группы; чужие или изменённые записи сохраняются.

Архивные состояния unit ограничены поддерживаемыми `enabled`, `disabled`, `static`. До мутаций проверяются точные unit-файлы, все стандартные systemd drop-in пути и граф `.wants`, `.requires`, `.upholds`; чужая активация блокирует план. После daemon-reload и перед действиями `DropInPaths` должен быть пустым, `FragmentPath` — точным восстановленным файлом. Web Agent bundles/журналы, marker и units возвращаются до активации его socket; связные broker socket/services готовы до Hub/Web/Gateway. Agent запускается после Compose, таймеры — последними. Перед commit повторно сверяются все восстановленные units, включая неактивные.

### Образы, активация и очередь команд

Проверка поддерживает legacy Docker tar, OCI и проверенные classic/OCI hybrid экспорты Docker 28/29. SHA-256 config/manifest/index/blob, RootFS diff IDs, платформа, точные сервисные теги и совместимые legacy metadata проверяются как связанный граф. Инертная v1 metadata допускается только при подтверждённой цепочке слоёв и конфигурации; лишние теги, файлы и неподдерживаемые варианты отвергаются. Локально проверены семь реальных экспортов Docker 28.5.2/29.5.2; это проверка форматов, а не общий успешный VM gate.

`docker load` получает только удерживаемый проверенный `images.tar` через явный локальный socket. Image ID может обозначать config, manifest либо index. Если импорт создаёт новый manifest ID, ограниченный анонимный повторный экспорт только фиксированных сервисных тегов подтверждает **тот же исходный config digest, RootFS и платформу** и связывает новый ID с проверенным графом. Compose получает реально исполнимый проверенный immutable ID через отдельный закрытый overlay, `--no-build --pull never` и метки ID/CAS восстановления. Одних совпавших слоёв или текста effective config недостаточно.

До импорта сохраняется ограниченный перечень уже существовавших image ID. Откат удаляет только новый принадлежащий операции immutable ID после повторной проверки; прежние образы, чужие теги, контейнеры, networks и volumes сохраняются. Перед остановкой/удалением Compose сверяются весь состав, метки, image/config hash и отсутствие чужих endpoints. `compose down`, `prune`, force removal и широкая очистка Docker не используются.

До **первой активации** карантин очереди создаёт частную копию SQLite с архивным WAL. Доверенный host Python работает в закрытом clone под UID/GID Hub `10001:10001` без дополнительных групп; сохраняет исходный journal mode `delete`/`wal`, отменяет все `queued` задания, очищает текст команды, удаляет ожидающие подтверждения Telegram и записывает только количества в аудит. Исходные DB/WAL/SHM остаются вне рабочего дерева до commit. Подмена исходного inode, неизвестная схема, триггеры, virtual tables или изменение производной базы блокируют автоматический возврат. Старые команды не должны исполниться при запуске восстановленного Hub.

Здоровье проверяется локальным HTTP, сохранённым CA для `https://localhost:8767`, контрактом SSH Gateway и Agent/systemd. Публичный TLS проверяется через локальный порт 443 с именем настроенного адреса; HTTPS старого сервера не может подтвердить новую цель. Законные записи Hub, Caddy и runtime-инвентарей после запуска допускаются при успешном commit. При последующей ошибке откат не удаляет изменившиеся данные: сохраняются данные, журнал и fence со статусом `recovery_required` для разбора root. Это не полный успешный откат.

`recover` проверяет точные inode/хеши, IDs и ownership и выполняет только обратные действия журнала. Повторный `start` читает сохранённый исход, а не повторяет установку. После полного `rolled_back` явный `retry` требует `terminal_sha256`, архивирует прежние журнал/план/Compose по их sealed inode/hash, выдаёт новый nonce и требует свежего preview/подтверждения. Прерванное архивирование сохраняет `retry_required`; `recovery_required` с изменёнными данными нельзя обойти новой попыткой.

### Поддерживаемые границы и проверки

Полное применение допускает только layout `full`, квитанцию v2 и чистую Ubuntu с systemd, root SSH либо заранее настроенным sudo без пароля. Hub-only, v1, неподдерживаемые file roots/enablement states, активная либо включённая в автозапуск VPN-маршрутизация, public staging ACME и изменение публичного адреса блокируются до мутаций. Неявного IP remapping нет; поддерживаемая VPN-конфигурация переносится с выключенными интерфейсами и требует отдельного включения.

**Рабочие изменяемые данные AmneziaWG не входят в переносимую копию.** Host archive сохраняет установочные журналы и локальную политику, но не актуальную конфигурацию/таблицу клиентов контейнера; AWG-образ также не экспортируется. План отказывает с `VPN_PORT_UNVERIFIED`. Это ограничение не следует обходить ручным удалением блокера или считать полным backup рабочих VPN-клиентов.

Локальные проверки покрывают журналируемые границы, partial shadow/owner, inode-подмены, дрейф родителей/NSS/паролей/групп, образов, Compose-меток и сети, свой/чужой fence и сохранение изменённых данных. Проверки транзакционных модулей не означают аварийное испытание каждой фазы на настоящей VM. Последний полный локальный Blueprint-набор: 949 тестов, 21 пропущен по окружению.

`tests/portable_restore_apply_vm.py` проверяет три сценария на одноразовой Ubuntu: смерть перед первым стартом службы и восстановление; независимое применение с переподключением клиента и проверкой Hub/Web/Agent/команд/файлов/PTY; ошибка здоровья после записи в SQLite с обязательным сохранением данных и fence. Для двух последних копий заранее создаются queued job и Telegram confirmation: проверяются карантин, аудит и отсутствие побочного файла старой команды. Проверка запускается только с явной provenance данной тестовой установки; очистка сверяет закрытый fixture ledger, source pin, paths/inode/NSS и IDs гостевых машин и не усыновляет новые ресурсы. SQLite-подключения выполняются под UID/GID Hub без дополнительных групп. Эти три сценария прошли [общий Ubuntu-прогон](https://github.com/sovagrid/sovagrid-blueprint/actions/runs/41332122229); подробности capability и границы выпуска приведены в [RELEASE_1_0.md](RELEASE_1_0.md). Локальные проверки транзакционных границ не означают аварийного испытания VM после каждой отдельной фазы.
