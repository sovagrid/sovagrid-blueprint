# Резервная копия управляемого состояния Ubuntu-хоста

`deploy/host_backup.py` — низкоуровневая root-only операция для полного **управляемого состояния SovaGrid** на одном хосте. Она дополняет снимки отдельной базы Hub в `/var/lib/sovagrid/backups`. Архив хоста содержит состояние Hub вместе с уже созданными снимками Hub, конфигурацию, ключи и сертификаты SovaGrid, политику broker, файлы systemd, необязательный marker управляемого SSH gateway и проверенный установленный `/opt/sovagrid-src`. Он хранится отдельно в `/var/lib/sovagrid-host-backups`, чтобы никогда не попасть в собственный обход.

Архив содержит секреты. Каталог имеет владельца `root:root` и режим `0700`; `.tar.gz` и `.manifest.json` имеют `root:root 0600`. JSON-ответ CLI показывает только идентификатор, время UTC, схему хоста, размер и число записей. Манифест содержит SHA-256 архива и digest установленного source manifest, без списка имён и содержимого секретов. Архив не имеет HTTP/API для скачивания.

## Граница схем

| Схема | Включено | Исключено |
|---|---|---|
| Full Hub+Agent | База Hub, снимки Hub и их root-only журналы, Caddy CA и ключи, пароль первого администратора, Agent config/token и его локальный код, управляемые WireGuard state/client keys, локальная политика Amnezia, VPN, service, routing и journal broker, точные unit-файлы | `/root/.ssh`, `/home`, пользовательские файлы Agent `/var/lib/sovagrid-agent/files`, сторонние Docker volumes, чужие VPN и systemd-службы |
| Hub-only + внешний Agent | База и снимки локального Hub, его Caddy CA, пароль администратора, локальный Agent config/token и код, локальные политики, точные unit-файлы, установленный source bundle | Конфиг, токен, CA, код, данные и SSH-туннель внешнего Agent; его WireGuard/Amnezia state и ключи; `/var/lib/sovagrid-agent-local/files` |

Если на Hub-only узле включён локальный сбор контейнеров, архив дополнительно содержит его root-owned состояние, точные два systemd unit и очищенный снимок `/var/lib/sovagrid-containers-local/snapshot.json`. Это только локальные данные; инвентарь внешнего Agent не копируется. Незавершённое включение или выключение коллектора блокирует создание архива до `recover`.

На обеих схемах установленный Web Agent входит в архив вместе с точными `sovagrid-web-agent-control.socket` и `.service`, root-owned marker `/var/lib/sovagrid/.web-agent-installer-managed-by-run-sh` и закрытым каталогом `/var/lib/sovagrid/web-agent`. Последний включает версионированные `source-<sha256>.tar.gz`, `jobs/<request-id>.json`, файлы блокировок и, если создан, `completed-enrollments.jsonl`. Каталоги должны быть `root:root 0700`, файлы — `root:root 0600`; каждый bundle сверяется с SHA-256 в имени. Неизвестные файлы, неверные режимы и частично установленное состояние блокируют архив. Безопасные остатки прерванной атомарной записи `.source-*` и `.enrollment-*` не включаются. Незавершённые установки удалённых Agent сохраняют локальный журнал для последующего возобновления, но состояние самого удалённого хоста остаётся вне этого архива.

Установленный `/opt/sovagrid-src` включается только если `source_manifest(..., allow_generated=True)` подтвердил весь release bundle. Дополнительный файл, symlink или несовпадающий hash прерывает операцию. Для хранилищ и конфигурации проверяются точные владельцы, режимы и отсутствие symlink, hardlink, сокетов, устройств и групповой/общей записи. Для `hub.sqlite`, bootstrap-пароля, Bot token и Hub-only политики проверяются особые режимы. Некоторый код и публичные сертификаты читаемы на хосте, но закрытый Caddy root защищён каталогом `0700`; весь выходной архив закрыт `0600`.

## Контракт для Connect

Исполнять только через проверенное root SSH-подключение и из root-owned установленного bundle:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py plan
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py source
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py create
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py list
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py verify <32-hex-id>
```

Успех — exit `0` и ровно одна строка JSON с `ok:true`, `protocol:"sovagrid-host-backup-v1"`. `plan` возвращает `layout`, `active_units` (точный перечень активных локальных writer units), `running_containers` (`[]`, `hub`/`web` или `hub`/`web`/`ssh-gateway`) и `offline_ready`. Gateway — необязательная третья служба: установки 0.6 без него остаются допустимы. Работающий gateway признаётся управляемым только при точном root:root `0600` marker `/var/lib/sovagrid/.ssh-gateway-managed-by-run-sh`; отсутствующий или повреждённый marker блокирует операцию. Запущенный Web Agent тоже требует точный root:root `0600` marker; его socket и service включены в локальные writer units. `source` возвращает digest установленного source manifest для проверки поколения перед запуском. `create` возвращает `archive` с `id`, `created_at` (ISO 8601 UTC), `layout`, `bytes`, `files`. `list` возвращает `archives`, в том числе пустой массив до первого создания, отсортированный по времени от новых к старым. `verify` возвращает те же поля `archive` и `verified:true`. Отказ — exit `40`, одна строка `{"ok":false,"protocol":"sovagrid-host-backup-v1","error":"CODE"}`. Основные коды: `ROOT_REQUIRED`, `BUSY`, `SERVICES_RUNNING`, `CONTAINERS_RUNNING`, `UNMANAGED_GATEWAY`, `UNSAFE_GATEWAY_MARKER`, `UNMANAGED_WEB_AGENT`, `UNSAFE_WEB_AGENT_MARKER`, `UNMANAGED_UNIT`, `UNKNOWN_ACTIVE_UNIT`, `CONTAINER_AMBIGUOUS`, `SOURCE_UNAVAILABLE`, `SOURCE_UNSAFE`, `UNSAFE_SOURCE`, `MISSING_SOURCE`, `SOURCE_CHANGED`, `DISK_SPACE`, `SIZE_LIMIT`, `FILE_LIMIT`, `TIME_LIMIT`, `NOT_FOUND`.

`plan` только читает состояние; его результат может устареть. `create` вновь проверяет схему, source manifest и активность служб после получения общих locks. На Hub-only узле первым берётся `/run/sovagrid-promotion.lock`, чтобы локальный коллектор не менялся во время архивации; затем следуют `/opt/sovagrid-candidates/.lock` и `/var/lib/sovagrid/.public-web.lock`. Работающий внешний Agent и обратный SSH-туннель внешнего Agent, а также `sovagrid-vpn-routing.service` не входят в набор локальных writer units и не останавливаются. SovaGrid Agent остаётся активным даже на Full-узле: в архив включены его статические конфигурации, а изменение установленного bundle блокируется общим lock и дополнительно обнаруживается повторной сверкой файлов. На Hub-only узле внешние Agent и туннель не участвуют в снимке.

Для согласованности низкоуровневый `create` требует остановленных Hub/Web/SSH gateway контейнеров и локальных writer timers/brokers из `plan`. Скрипт сам не меняет службы. Графический клиент пользуется отдельным root-only `host_backup_orchestrator.py`: он ведёт долговечный журнал запроса, запускает операцию под transient systemd unit, останавливает только перечень из повторно проверенного плана, вызывает `_create_locked()` с заранее записанным ID архива и снова запускает ранее работавшие контейнеры и units. Таймер после включения может кратко активировать собственную одноразовую службу; это не считается потерей исходного состояния. Внешний Agent, обратный туннель внешнего Agent и VPN routing не останавливаются. Если изначально запущен неполный состав Hub/Web, с gateway или без него, либо работает одноразовый writer service, операция отказывается до простоя. Неизвестные контейнеры с Compose project label `sovagrid` тоже блокируют операцию.

Контракт графического клиента после подтверждения:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py start <32-hex-request-id> <64-hex-installed-source-manifest>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py status <32-hex-request-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py list
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py recover <32-hex-request-id>
```

Ответ записи операции: `ok`, `protocol:"sovagrid-host-backup-operation-v1"`, `request_id`, `phase`, `archive` (либо `null`), `error` (либо `null`), `created_at` в UTC. `list` возвращает до 100 таких записей в `operations`. `start` с тем же UUID лишь читает журнал и никогда не повторяет создание. После потерянного SSH-ответа клиент читает `status` или `list`. Фазы `complete`, `recovered`, `failed` терминальны; `recovery_required` указывает на отдельное `recover`, которое **только** восстанавливает службы, а не повторяет архив. При аварийном прерывании архив определяется по заранее записанному ID, а удаляться могут только его неполные временные файлы. Если исходники, unit-файлы или container ID изменились, автоматическое восстановление откажется, сохраняя журнал для разбора. Для gateway проверяется его Compose service label, прежний container ID и Docker healthcheck; gateway с новым ID не подменит остановленный экземпляр. Готовый архив всё ещё можно читать только от root на самом сервере.

У root CLI есть отдельный режим start-portable с UUID запроса и SHA-256 установленного манифеста, а также portable-status с тем же UUID. Он требует работающие управляемые Hub/Web и необязательный gateway, закрепляет исходные container/image ID и SHA-256 вектора RootFS слоёв каждого точного локального тега, создаёт архив, восстанавливает и проверяет службы, затем под теми же блокировками экспортирует образы. Исходные container/image ID, теги и RootFS сверяются после экспорта. Затем он атомарно публикует закрытый `receipt.json` внутри каталога образов и только после этого записывает `complete` в журнал. Квитанция содержит SHA-256 обоих артефактов, исходного кода, unit/container/image ID, RootFS и отдельно digest экспортированной конфигурации; она переносится вместе с образом на чистый хост без исходного журнала. Ошибка экспорта или публикации квитанции даёт `failed/IMAGES_FAILED`, сохраняя основной архив для отдельной проверки; recover не повторяет экспорт и не выдаёт `complete`. Перед переносом root повторяет `verify` архива и `verify-portable` образов. Старые start/status и ответы Connect не меняются; кнопка панели пока запускает обычный архив.

## Доступ из веб-панели

Полный администратор локального Hub видит в настройках план остановки, список закрытых архивов и операций, проверку целостности, запуск и восстановление служб. Hub передаёт root broker только фиксированные действия и идентификаторы; содержимое архива и секреты не выдаются по HTTP. Запуск и `recover` записываются в аудит. Браузер сохраняет UUID запроса до POST, чтобы после временной остановки Hub/Web проверить ту же операцию без повторного создания. Если Hub не вернулся, Web не может выполнить `recover`; используйте Connect по SSH с тем же UUID. Каталог журнала `/var/lib/sovagrid-host-backup-operations` создаёт установщик с `root:root 0700` до запуска broker.

Лимиты: 20 000 записей, 8 GiB суммарного содержимого и готового архива, 4 GiB на один файл, 300 секунд на source check/обход/запись, 60 секунд на проверку release source, минимум 256 MiB запаса диска сверх несжатого размера, максимум 100 архивов. При отказе временные файлы и частично опубликованный архив удаляются. `verify` проверяет SHA-256 готового архива и структуру tar; восстановления файлов в рабочие пути этот выпуск не выполняет. Gateway не имеет отдельного persistent volume; Docker images Hub/Web/Gateway не входят в основной архив. Для них есть отдельный закрытый экспорт ниже. Архив представляет состояние SovaGrid, а не образ всего диска Ubuntu.

## Отдельный экспорт Docker-образов

После успешного архива и перезапуска контейнеров root может выполнить:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py create <32-hex-host-archive-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py verify <32-hex-host-archive-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py verify-portable <32-hex-host-archive-id>
```

`create` под общими locks обновления заново проверяет основной host archive и его установленный source digest. Затем он требует полный работающий Compose stack (`hub`, `web` и, если есть проверенный marker, `ssh-gateway`), сверяет для каждого сервиса image ID работающего контейнера с точным тегом `sovagrid-<service>:local`, берёт у тега упорядоченный `RootFS.Layers` и повторяет обе проверки после экспорта. `docker image save` получает только эти точные теги; image config и слои проверяются по SHA-256, а чужие теги, лишние tar-файлы и неподдерживаемые платформы отклоняются. Docker может преобразовать конфигурацию при OCI-экспорте: digest её blob не обязан совпадать с исходным daemon image ID. Поэтому манифест раздельно сохраняет исходный image ID и экспортированный config digest, а связь с запущенным тегом проверяет через SHA-256 исходного и экспортированного вектора `RootFS.Layers`/`rootfs.diff_ids`. Это подтверждает тождество слоёв и закрепление тега во время экспорта, но не полную эквивалентность всех полей конфигурации Docker. Если версия исходников, состав/ID контейнеров, теги или RootFS изменились, операция отказывает и удаляет своё временное дерево. Экспорт не останавливает службы.

Артефакт публикуется одним rename в `/var/lib/sovagrid-host-image-exports/<id>/`: `images.tar` и `manifest.json` внутри имеют `root:root 0600`, каталоги — `root:root 0700`. Режим `start-portable` дополнительно атомарно добавляет `receipt.json` с теми же правами. Манифест связывает экспорт с ID, SHA-256 и source digest основного архива и содержит точные исходные image/container IDs, `exported_configs`, `rootfs_sha256`, размер, число tar-записей, SHA-256 образов и время UTC. Для переноса нужны все три файла каталога экспорта, а также `<id>.tar.gz` и `<id>.manifest.json` из `/var/lib/sovagrid-host-backups`; права root и режимы необходимо сохранить. Файлы не доступны по HTTP. Лимиты: 8 GiB для потока Docker и суммарной распаковки gzip-слоёв при проверке, 20 000 tar-записей, 1200 секунд, не менее 256 MiB свободного места после очередного блока записи, 8 KiB на квитанцию. Уже опубликованный ID не перезаписывается. При обычном отказе удаляется только свой временный каталог; после аварийного завершения скрытый временный каталог остаётся для ручного разбора root.

`verify` работает и на чистом Ubuntu-хосте без Docker daemon. Он заново проверяет основной архив, закрытые метаданные и SHA-256 полного `images.tar`, все пути и типы внешнего Docker tar, его `manifest.json`, SHA-256 каждого image config и `rootfs.diff_ids` каждого объявленного layer. Поддерживаются legacy Docker tar и проверенный вариант OCI tar, который создаёт Docker на Ubuntu: каждый blob сверяется с digest/size OCI descriptor, gzip-слои ограниченно распаковываются для проверки diff ID, чужие теги и неперечисленные файлы запрещены. `verify-portable` дополнительно требует квитанцию, сверяет её поля с обоими артефактами и выдаёт исходные active units, container/image IDs и проверенную платформу каждого образа в `platforms`; ему не нужен журнал исходного сервера. Это проверка сохранённых байтов, а не доказательство происхождения копии: перед переносом следует удостоверить источник пары по защищённому каналу. Каталог экспорта исключён из проверки занятости `clean-plan`, поскольку это входные данные для восстановления. В этом выпуске **нет** `docker load`, переключения тегов, установки файлов или запуска контейнеров; `apply_available:false` сохраняется. Основной архив сам по себе по-прежнему выдаёт блокер `DOCKER_IMAGES_NOT_INCLUDED`. Экспорт ещё не привязан к кнопке создания архива в панели: его вызывают отдельной root-only командой после завершения операции архивации.

## Предпросмотр восстановления на чистом хосте

`deploy/host_restore.py clean-plan <32-hex-id>` — отдельная **только читающая** проверка перенесённой пары `<id>.tar.gz` и `<id>.manifest.json` в закрытом `/var/lib/sovagrid-host-backups`. Обе копии должны принадлежать `root:root`, иметь режим `0600` и не быть symlink/hardlink; каталог — `root:root 0700`. Скрипт запускается от root из независимо проверенного исходного пакета SovaGrid, а не из ещё не проверенного архива. Схему исходников проверяющего пакета следует сверить с версией архива. Сам SHA-256 внутри пары обнаруживает повреждение, но не удостоверяет происхождение архива.

Режим заново сверяет хеш сжатого архива, каждый путь, тип, владельца и режим tar-записи, обязательные закрытые данные, встроенный `sovagrid-bundle.json` и SHA-256 всех исходников. Он не распаковывает файлы. Для Agent config/token проверяется одинаковый ненулевой числовой GID из архива; для локального Agent в Hub-only тот же GID требуется и у `hub-ca.pem`. Группа ещё не обязана существовать на чистом хосте. Затем только чтением проверяется, что пути управляемого состояния и пространства имён SovaGrid на целевом хосте отсутствуют; symlink либо групповой/общедоступный для записи родительский каталог отмечается отдельно. Каталог с самой перенесённой резервной копией исключён из проверки занятости. Дополнительно проверяются занятые UID/GID обязательных учётных записей, группа Web Agent и числовой GID Agent из самого архива через системный NSS; несовпадение даёт `TARGET_IDENTITY_CONFLICT` и закрывает `target_empty`. Результат содержит `verified`, `target_empty`, число конфликтов путей, число небезопасных путей, число конфликтов учётных записей и фиксированные коды блокировок без имён или содержимого секретных файлов. Изолированная фикстура проверила чистый временный root, занятый каталог, чужой GID Agent, неизвестный `sovagrid-*.service` и symlink родителя без распаковки.

После успешного `clean-plan` root может выполнить `deploy/host_restore.py stage <id>`. Команда повторно проверяет архив из того же открытого file descriptor, проверяет запас диска, создаёт закрытое дерево `/var/lib/.sovagrid-host-restore-staging/<id>` и атомарно публикует его после извлечения. Внутри дерева все файлы имеют `root:root 0600`, каталоги — `root:root 0700`, независимо от исходных владельцев и режимов; исходная метаинформация остаётся в архиве. Перед публикацией digest дерева сверяется с независимо вычисленным из проверенного архива ожидаемым digest, включая все созданные родительские каталоги; `stage-status` повторяет эту сверку. Это обнаруживает даже неверные байты, попавшие в дерево до первой записи квитанции. Распаковка не пишет в `/etc`, `/opt`, `/usr/local`, рабочие `/var/lib/sovagrid*`, не создаёт пользователей и не запускает службы. При отказе команда удаляет только своё временное дерево. `stage-status <id>` повторно проверяет исходный архив и содержимое закрытого дерева, включая посторонние или изменённые файлы; результат выдаёт только счётчики и фиксированные коды. Снимок стадии содержит закрытый `receipt.json` с digest дерева, SHA-256 архива и временем UTC. Стадия с тем же ID повторно не перезаписывается (`STAGE_EXISTS`); если процесс погиб до публикации, его закрытый временный каталог остаётся для ручного разбора root и не принимается за завершённую стадию.

`deploy/host_restore.py portable-clean-plan <32-hex-id>` добавляет к этой проверке переносимый экспорт: требует рядом с `images.tar` и `manifest.json` точный `receipt.json`, повторно сверяет оба архива, SHA-256 и платформы образов. Команда только читает Docker daemon, имена образов/контейнеров/сетей/томов, слушающие TCP-порты 80, 443, 8766 и 8767, UDP-порты управляемых WireGuard-инстансов из проверенного архива и доступное место. Порты извлекаются из ограниченного по размеру `state.json` и сверяются с `server.conf`; неоднозначное состояние VPN, включая внешнюю конфигурацию Amnezia, даёт `VPN_PORT_UNVERIFIED` и закрывает `target_empty`. Учитываются контейнеры как нового, так и старого формата Docker Compose. Команда сообщает счётчики конфликтов, совместимость архитектуры, `review_sha256` для точного подтверждения и коды блокировок без вывода сторонних имён. Отсутствующий Docker, несовместимая платформа, занятые ресурсы или недостаток места закрывают план. Проверка места закладывает запас на распаковку образов; перед будущим применением его придётся пересчитать. Основной `clean-plan` сохраняет прежнее поведение и блокер `DOCKER_IMAGES_NOT_INCLUDED`.

На чистом хосте root может выполнить `deploy/host_restore.py portable-stage <id> <review_sha256>` после просмотра переносимого плана. Команда отклоняет устаревший digest и любые блокеры кроме `APPLY_NOT_IMPLEMENTED`, повторно проверяет архив при создании закрытого дерева, затем сохраняет отдельную закрытую квитанцию, связывающую digest плана, SHA-256 архива, исходников, образов, точных `manifest.json` и `receipt.json` экспорта и дерева стадии. Метаданные экспорта читаются через закрытые file descriptor под общей блокировкой каталога и повторно сравниваются после полной проверки пары. `portable-stage-status <id>` заново проверяет дерево и переносимую пару, включая неизменность обоих файлов метаданных и хеши staged systemd unit, перечисленных в portable receipt; образы остаются в исходном закрытом каталоге, а не копируются второй раз. После прерывания между стадией архива и квитанцией тот же запрос можно безопасно повторить. Ни одна из команд не импортирует Docker-образы и не пишет в рабочие пути.

`deploy/host_restore.py portable-apply-preview <id>` повторно проверяет готовую стадию и состояние чистого хоста, возвращая `apply_review_sha256`, число конфликтов, список ранее активных управляемых unit и `target_ready`. Digest связывает текущий план цели с точными хешами стадии, архива, Docker tar и двух файлов метаданных экспорта. Изменение цели, архива, квитанции или unit-файлов даёт новый digest либо отказ. Этот digest пока не принимает никакая команда применения: `apply_available:false` и `APPLY_NOT_IMPLEMENTED` остаются в ответе. Проверка может занять время, потому что повторно читает оба архива и дерево стадии.

`apply_available` всегда `false`: **команды установки в рабочие пути нет**. Даже `target_empty:true`, успешный `stage-status` и проверенная переносимая пара не гарантируют рабочую сеть и будущий старт служб; архив не является образом Ubuntu. Проверка пустоты целевого хоста — снимок состояния, который может устареть сразу после ответа. Для полноценного восстановления ещё нужны транзакция с блокировкой записывающих служб, выделение UID/GID из архива, безопасный импорт и закрепление экспортированных образов, установка с записью каждого шага в durable journal, проверка здоровья и журналируемый откат. Docker `load` может оставить слои и теги даже после неуспеха; предварительная чистота имён ещё не даёт безопасной операции отката. `stage` не является восстановлением, поэтому не останавливает службы и не меняет рабочую установку.

Будущий `apply` должен вернуть закрытый каталог Web Agent и журнал заданий до запуска его службы, сверить SHA-256 каждого versioned bundle, затем установить marker и оба systemd unit. Группу сокета `sovagrid-web-agent` с GID `10005` нужно создать до активации socket; socket и service должны быть готовы до запуска Hub/Web с bind mount сокета. Начинать удалённые установки из сохранённого журнала можно только после восстановления локального Hub и проверки прежнего SSH host key. Текущие `clean-plan`, `stage` и `stage-status` лишь проверяют и подготавливают данные; такой порядок ещё не реализован как команда восстановления.

### Контракт следующей транзакции восстановления

Этот раздел описывает **ещё не реализованный** `portable-apply`, чтобы его можно было проверить отдельно до включения команды. Исполнитель должен принимать только `<id>` и `apply_review_sha256` из `portable-apply-preview`, брать exclusive lock закрытого каталога стадий и повторять все проверки уже под lock. Для отсутствия гонки с другой установкой каждая публикация в рабочий путь должна использовать `renameat2(RENAME_NOREPLACE)` относительно проверенного file descriptor родительского каталога и повторную проверку того, что источник всё ещё совпадает со стадией. Нельзя передавать пути из архива в shell или делать рекурсивное копирование по непроверенному пути.

Публикуемые ресурсы ограничены проверенными архивными записями под `/etc/sovagrid*`, `/var/lib/sovagrid*`, `/opt/sovagrid-*` и точными leaf-файлами `sovagrid-*` в `/etc/systemd/system`, `70-sovagrid-vpn-routing.conf` в `/etc/sysctl.d`, `sovagrid-vpn-ctl` в `/usr/local/bin` и `sovagrid-vpn-broker` в `/usr/local/libexec`. Каталоги перед публикацией должны находиться в закрытых shadow-каталогах **на той же файловой системе, что их адресат**. Метаданные владельца, группы и режима восстанавливаются из повторно проверенного tar, байты — из стадии, чей digest уже независимо вычислен из tar. Любой другой существующий SovaGrid-путь, symlink или опасный родитель блокирует команду. Создаваемые родительские каталоги тоже входят в журнал и удаляются при откате только если они пусты и принадлежат этой операции.

До первого изменения исполнитель должен синхронно записать закрытый журнал с ID, обоими CAS, точными SHA-256 всех пяти входных файлов, layout, manifest ресурсов и снимком отсутствующих имён Docker/путей/NSS. Каждая следующая запись состояния выполняется через отдельный `0600` temporary, `fsync(file)`, атомарный rename и `fsync(directory)`; перед каждой внешней операцией сохраняется её intent. Предлагаемые фазы: `prepared` → `identities_reserved` → `images_loaded` → `files_switched` → `services_started` → `healthy` → `committed`. При отказе или повторном запуске `recover` сверяет точные inode/хеши созданных файлов, числовые UID/GID, Docker tag→image ID и управляемые unit, затем откатывает в обратном порядке. Если ресурс отличается от ожидаемого после вмешательства другого процесса, `recover` оставляет журнал в `recovery_required` и ничего чужого не удаляет. Прерванный `prepared` удаляет только закрытые shadow-каталоги; успешный `committed` не запускается повторно.

Импорт `images.tar` должен читать уже открытый проверенный FD, удерживать lock входной пары, после `docker image load` проверить каждый тег `sovagrid-<service>:local` по **экспортированному config digest** (`exported_configs`), `RootFS.Layers`, платформе и точному составу сервисов. Исходный Docker image ID в квитанции может отличаться от экспортированного config digest при OCI-конвертации, поэтому его нельзя слепо сравнивать с новым daemon ID. Откат снимает только теги, совпадающие с записанными экспортированными digest; неиспользуемые слои Docker может оставить до отдельной очистки. `systemctl daemon-reload`, включение и старт unit, `docker compose up -d --no-build` и health-check Hub/Web/Gateway выполняются только после публикации всех файлов и закрытого журнала; Web Agent socket поднимается до Hub/Web. Любая ошибка здоровья запускает откат, а не выдаёт `complete`.

Сейчас не хватает двух данных/механизмов для безопасного запуска: portable receipt хранит `active_units`, но не прежний `is-enabled` каждого unit (enablement symlink не архивируется); обычный `run.sh` сам создаёт состояние и секреты, а не устанавливает только системные зависимости для restore. Требуются новая версия квитанции с enablement и режим установщика `dependencies-only` либо отдельный проверенный список зависимостей. До них и до проверки аварийного завершения после **каждой** фазы на одноразовом Ubuntu-хосте `portable-apply` остаётся выключенным. Локальные тесты этой стадии уже покрывают порчу staged-байтов до первой квитанции, подмену receipt/manifest экспорта, изменение хеша systemd unit и устаревший CAS цели.
