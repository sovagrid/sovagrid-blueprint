# Резервная копия управляемого состояния Ubuntu-хоста

`deploy/host_backup.py` — низкоуровневая root-only операция для полного **управляемого состояния SovaGrid** на одном хосте. Она дополняет снимки отдельной базы Hub в `/var/lib/sovagrid/backups`. Архив хоста содержит состояние Hub вместе с уже созданными снимками Hub, конфигурацию, ключи и сертификаты SovaGrid, политику broker, файлы systemd, необязательный marker управляемого SSH gateway и проверенный установленный `/opt/sovagrid-src`. Он хранится отдельно в `/var/lib/sovagrid-host-backups`, чтобы никогда не попасть в собственный обход.

Архив содержит секреты. Каталог имеет владельца `root:root` и режим `0700`; `.tar.gz` и `.manifest.json` имеют `root:root 0600`. JSON-ответ CLI показывает только идентификатор, время UTC, схему хоста, размер и число записей. Манифест содержит SHA-256 архива и digest установленного source manifest, без списка имён и содержимого секретов. Обычный архив не имеет HTTP/API для скачивания; отдельная переносимая операция доступна в Web после проверки и одноразовой авторизации.

**Статус версий:** описанные ниже квитанция переносимой копии v2 и режим подготовки зависимостей добавлены в исходники после опубликованного `server-v0.14.1`. Они ещё не входят в стабильный архив или однокомандную установку. Стабильный выпуск по-прежнему предоставляет создание и скачивание пяти файлов, проверку, стадию и предпросмотр восстановления; команды полного применения нет ни в нём, ни в текущих исходниках.

## Граница схем

| Схема | Включено | Исключено |
|---|---|---|
| Full Hub+Agent | База Hub, снимки Hub и их root-only журналы, Caddy CA и ключи, пароль первого администратора, Agent config/token и его локальный код, управляемые WireGuard state/client keys, локальная политика Amnezia, VPN, service, routing и journal broker, точные unit-файлы | `/root/.ssh`, `/home`, пользовательские файлы Agent `/var/lib/sovagrid-agent/files`, сторонние Docker volumes, чужие VPN и systemd-службы |
| Hub-only + внешний Agent | База и снимки локального Hub, его Caddy CA, пароль администратора, локальный Agent config/token и код, локальные политики, точные unit-файлы, установленный source bundle | Конфиг, токен, CA, код, данные и SSH-туннель внешнего Agent; его WireGuard/Amnezia state и ключи; `/var/lib/sovagrid-agent-local/files` |

Если на Hub-only узле включён локальный сбор контейнеров, архив дополнительно содержит его root-owned состояние, точные два systemd unit и очищенный снимок `/var/lib/sovagrid-containers-local/snapshot.json`. Это только локальные данные; инвентарь внешнего Agent не копируется. Незавершённое включение или выключение коллектора блокирует создание архива до `recover`.

На обеих схемах установленный Web Agent входит в архив вместе с точными `sovagrid-web-agent-control.socket` и `.service`, root-owned marker `/var/lib/sovagrid/.web-agent-installer-managed-by-run-sh` и закрытым каталогом `/var/lib/sovagrid/web-agent`. Последний включает версионированные `source-<sha256>.tar.gz`, `jobs/<request-id>.json`, файлы блокировок и, если создан, `completed-enrollments.jsonl`. Каталоги должны быть `root:root 0700`, файлы — `root:root 0600`; каждый bundle сверяется с SHA-256 в имени. Неизвестные файлы, неверные режимы и частично установленное состояние блокируют архив. Безопасные остатки прерванной атомарной записи `.source-*` и `.enrollment-*` не включаются. Незавершённые установки удалённых Agent сохраняют локальный журнал для последующего возобновления, но состояние самого удалённого хоста остаётся вне этого архива.

Установленный `/opt/sovagrid-src` включается только если `source_manifest(..., allow_generated=True)` подтвердил весь release bundle. Дополнительный файл, symlink или несовпадающий hash прерывает операцию. Для хранилищ и конфигурации проверяются точные владельцы, режимы и отсутствие symlink, hardlink, сокетов, устройств и групповой/общей записи. Для `hub.sqlite`, bootstrap-пароля, Bot token и Hub-only политики проверяются особые режимы. Некоторый код и публичные сертификаты читаемы на хосте, но закрытый Caddy root защищён каталогом `0700`; весь выходной архив закрыт `0600`.

## Контракт для Connect

Исполнять только через проверенное root SSH-подключение и из root-owned установленного bundle:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py plan
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py source
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py create
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py list
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup.py verify <32-hex-id>
```

Успех — exit `0` и ровно одна строка JSON с `ok:true`, `protocol:"sovagrid-host-backup-v1"`. `plan` возвращает `layout`, `active_units` (точный перечень активных локальных writer units), `running_containers` (`[]`, `hub`/`web` или `hub`/`web`/`ssh-gateway`) и `offline_ready`. Gateway — необязательная третья служба: установки 0.6 без него остаются допустимы. Работающий gateway признаётся управляемым только при точном root:root `0600` marker `/var/lib/sovagrid/.ssh-gateway-managed-by-run-sh`; отсутствующий или повреждённый marker блокирует операцию. Запущенный Web Agent тоже требует точный root:root `0600` marker; его socket и service включены в локальные writer units. `source` возвращает digest установленного source manifest для проверки поколения перед запуском. `create` возвращает `archive` с `id`, `created_at` (ISO 8601 UTC), `layout`, `bytes`, `files`. `list` возвращает `archives`, в том числе пустой массив до первого создания, отсортированный по времени от новых к старым. `verify` возвращает те же поля `archive` и `verified:true`. Отказ — exit `40`, одна строка `{"ok":false,"protocol":"sovagrid-host-backup-v1","error":"CODE"}`. Основные коды: `ROOT_REQUIRED`, `BUSY`, `SERVICES_RUNNING`, `CONTAINERS_RUNNING`, `UNMANAGED_GATEWAY`, `UNSAFE_GATEWAY_MARKER`, `UNMANAGED_WEB_AGENT`, `UNSAFE_WEB_AGENT_MARKER`, `UNMANAGED_UNIT`, `UNKNOWN_ACTIVE_UNIT`, `CONTAINER_AMBIGUOUS`, `SOURCE_UNAVAILABLE`, `SOURCE_UNSAFE`, `UNSAFE_SOURCE`, `MISSING_SOURCE`, `SOURCE_CHANGED`, `DISK_SPACE`, `SIZE_LIMIT`, `FILE_LIMIT`, `TIME_LIMIT`, `NOT_FOUND`.

`plan` только читает состояние; его результат может устареть. `create` вновь проверяет схему, source manifest и активность служб после получения общих locks. На Hub-only узле первым берётся `/run/sovagrid-promotion.lock`, чтобы локальный коллектор не менялся во время архивации; затем следуют `/opt/sovagrid-candidates/.lock` и `/var/lib/sovagrid/.public-web.lock`. Работающий внешний Agent и обратный SSH-туннель внешнего Agent, а также `sovagrid-vpn-routing.service` не входят в набор локальных writer units и не останавливаются. SovaGrid Agent остаётся активным даже на Full-узле: в архив включены его статические конфигурации, а изменение установленного bundle блокируется общим lock и дополнительно обнаруживается повторной сверкой файлов. На Hub-only узле внешние Agent и туннель не участвуют в снимке.

Для согласованности низкоуровневый `create` требует остановленных Hub/Web/SSH gateway контейнеров и локальных writer timers/brokers из `plan`. Скрипт сам не меняет службы. Графический клиент пользуется отдельным root-only `host_backup_orchestrator.py`: он ведёт долговечный журнал запроса, запускает операцию под transient systemd unit, останавливает только перечень из повторно проверенного плана, вызывает `_create_locked()` с заранее записанным ID архива и снова запускает ранее работавшие контейнеры и units. Таймер после включения может кратко активировать собственную одноразовую службу; это не считается потерей исходного состояния. Внешний Agent, обратный туннель внешнего Agent и VPN routing не останавливаются. Если изначально запущен неполный состав Hub/Web, с gateway или без него, либо работает одноразовый writer service, операция отказывается до простоя. Неизвестные контейнеры с Compose project label `sovagrid` тоже блокируют операцию.

Контракт графического клиента после подтверждения:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py start <32-hex-request-id> <64-hex-installed-source-manifest>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py status <32-hex-request-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py list
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_backup_orchestrator.py recover <32-hex-request-id>
```

Ответ записи операции: `ok`, `protocol:"sovagrid-host-backup-operation-v1"`, `request_id`, `phase`, `archive` (либо `null`), `error` (либо `null`), `created_at` в UTC. `list` возвращает до 100 таких записей в `operations`. `start` с тем же UUID лишь читает журнал и никогда не повторяет создание. После потерянного SSH-ответа клиент читает `status` или `list`. Фазы `complete`, `recovered`, `failed` терминальны; `recovery_required` указывает на отдельное `recover`, которое **только** восстанавливает службы, а не повторяет архив. При аварийном прерывании архив определяется по заранее записанному ID, а удаляться могут только его неполные временные файлы. Если исходники, unit-файлы или container ID изменились, автоматическое восстановление откажется, сохраняя журнал для разбора. Для gateway проверяется его Compose service label, прежний container ID и Docker healthcheck; gateway с новым ID не подменит остановленный экземпляр. Готовый архив всё ещё можно читать только от root на самом сервере.

У root CLI есть отдельный режим start-portable с UUID запроса и SHA-256 установленного манифеста, а также portable-status с тем же UUID. Он требует работающие управляемые Hub/Web и необязательный gateway, закрепляет исходные container/image ID и SHA-256 вектора RootFS слоёв каждого точного локального тега, создаёт архив, восстанавливает и проверяет службы, затем под теми же блокировками экспортирует образы. Исходные container/image ID, теги и RootFS сверяются после экспорта. Затем он атомарно публикует закрытый `receipt.json` внутри каталога образов и только после этого записывает `complete` в журнал. Квитанция содержит SHA-256 обоих артефактов, исходного кода, unit/container/image ID, RootFS и отдельно digest экспортированной конфигурации; она переносится вместе с образом на чистый хост без исходного журнала. В новых исходниках `start-portable` создаёт квитанцию `sovagrid-portable-host-receipt-v2`: поле `unit_states` связывает каждый присутствующий точный управляемый systemd unit (из перечня до 24 для Full и до 20 для Hub-only) с `active` (булево), строкой `enablement` из ограниченного списка состояний systemd и SHA-256 его файла. Запись состояния до остановки служб и повторная сверка не дают подменить даже неактивный unit; v2 сверяется с байтами unit-файлов внутри основного архива. Ошибка экспорта или публикации квитанции даёт `failed/IMAGES_FAILED`, сохраняя основной архив для отдельной проверки; recover не повторяет экспорт и не выдаёт `complete`. Перед переносом root повторяет `verify` архива и `verify-portable` образов. Старые start/status и ответы Connect не меняются; в Web есть отдельная кнопка создания переносимой копии.

## Доступ из веб-панели

Полный администратор локального Hub видит в настройках план остановки, список закрытых архивов и операций, проверку целостности, запуск и восстановление служб. Hub передаёт root broker только фиксированные действия и идентификаторы. Обычный архив не выдаётся по HTTP. Для переносимой операции Web дополнительно вызывает root-проверку и выдаёт короткое одноразовое разрешение на скачивание выбранного файла в том же сеансе и origin Hub; архив содержит секреты. Запуск и `recover` записываются в аудит. Браузер сохраняет UUID запроса до POST, чтобы после временной остановки Hub/Web проверить ту же операцию без повторного создания. Если Hub не вернулся, Web не может выполнить `recover`; используйте Connect по SSH с тем же UUID. Каталог журнала `/var/lib/sovagrid-host-backup-operations` создаёт установщик с `root:root 0700` до запуска broker.

Лимиты: 20 000 записей, 8 GiB суммарного содержимого и готового архива, 4 GiB на один файл, 300 секунд на source check/обход/запись, 60 секунд на проверку release source, минимум 256 MiB запаса диска сверх несжатого размера, максимум 100 архивов. При отказе временные файлы и частично опубликованный архив удаляются. `verify` проверяет SHA-256 готового архива и структуру tar; восстановления файлов в рабочие пути этот выпуск не выполняет. Gateway не имеет отдельного persistent volume; Docker images Hub/Web/Gateway не входят в основной архив. Для них есть отдельный закрытый экспорт ниже. Архив представляет состояние SovaGrid, а не образ всего диска Ubuntu.

## Отдельный экспорт Docker-образов

После успешного архива и перезапуска контейнеров root может выполнить:

```text
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py create <32-hex-host-archive-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py verify <32-hex-host-archive-id>
python3 -I /opt/sovagrid-src/sovagrid-blueprint/deploy/host_image_export.py verify-portable <32-hex-host-archive-id>
```

`create` под общими locks обновления заново проверяет основной host archive и его установленный source digest. Затем он требует полный работающий Compose stack (`hub`, `web` и, если есть проверенный marker, `ssh-gateway`), сверяет для каждого сервиса image ID работающего контейнера с точным тегом `sovagrid-<service>:local`, берёт у тега упорядоченный `RootFS.Layers` и повторяет обе проверки после экспорта. `docker image save` получает только эти точные теги; image config и слои проверяются по SHA-256, а чужие теги, лишние tar-файлы и неподдерживаемые платформы отклоняются. В Docker с containerd ID образа может обозначать manifest или index, поэтому он не обязан совпадать с digest конфигурации. Манифест раздельно сохраняет исходный ID и config digest. Проверка связывает ID с криптографически проверенным графом config/manifest/index данного сервиса, сверяет точные теги, платформу и исходный/экспортированный векторы `RootFS.Layers`/`rootfs.diff_ids`. Одного совпадения слоёв для этой привязки недостаточно. Если версия исходников, состав/ID контейнеров, теги или RootFS изменились, операция отказывает и удаляет своё временное дерево. Экспорт не останавливает службы.

Артефакт публикуется одним rename в `/var/lib/sovagrid-host-image-exports/<id>/`: `images.tar` и `manifest.json` внутри имеют `root:root 0600`, каталоги — `root:root 0700`. Режим `start-portable` дополнительно атомарно добавляет `receipt.json` с теми же правами. Манифест связывает экспорт с ID, SHA-256 и source digest основного архива и содержит точные исходные image/container IDs, `exported_configs`, `rootfs_sha256`, размер, число tar-записей, SHA-256 образов и время UTC. Для переноса нужны все три файла каталога экспорта, а также `<id>.tar.gz` и `<id>.manifest.json` из `/var/lib/sovagrid-host-backups`; права root и режимы необходимо сохранить. Web выдаёт все пять файлов отдельными одноразовыми загрузками с точными именами. На целевом хосте разместите `<id>.tar.gz` и `<id>.manifest.json` в `/var/lib/sovagrid-host-backups/`, а `images.tar`, `manifest.json` и `receipt.json` — в `/var/lib/sovagrid-host-image-exports/<id>/`; затем запустите проверку и предпросмотр восстановления. Лимиты: 8 GiB для потока Docker и суммарной распаковки gzip-слоёв при проверке, 20 000 tar-записей, 1200 секунд, не менее 256 MiB свободного места после очередного блока записи, 8 KiB на квитанцию. Уже опубликованный ID не перезаписывается. При обычном отказе удаляется только свой временный каталог; после аварийного завершения скрытый временный каталог остаётся для ручного разбора root.

`verify` работает и на чистом Ubuntu-хосте без Docker daemon. Он заново проверяет основной архив, закрытые метаданные и SHA-256 полного `images.tar`, все пути и типы внешнего Docker tar, его `manifest.json`, SHA-256 каждого image config и `rootfs.diff_ids` каждого объявленного layer. Поддерживаются legacy Docker tar и проверенный вариант OCI tar, который создаёт Docker на Ubuntu: каждый blob сверяется с digest/size OCI descriptor, gzip-слои ограниченно распаковываются для проверки diff ID, чужие теги и неперечисленные файлы запрещены. `verify-portable` дополнительно требует квитанцию, сверяет её поля с обоими артефактами и выдаёт исходные active units, container/image IDs и проверенную платформу каждого образа в `platforms`; ему не нужен журнал исходного сервера. Это проверка сохранённых байтов, а не доказательство происхождения копии: перед переносом следует удостоверить источник пары по защищённому каналу. Каталог экспорта исключён из проверки занятости `clean-plan`, поскольку это входные данные для восстановления. В этом выпуске **нет** `docker load`, переключения тегов, установки файлов или запуска контейнеров; `apply_available:false` сохраняется. Основной архив сам по себе по-прежнему выдаёт блокер `DOCKER_IMAGES_NOT_INCLUDED`. Панель может запустить `start-portable` и проверить результат. Для уже существующего обычного архива отдельный экспорт образов вызывается root-only командой после завершения архивации.

## Предпросмотр восстановления на чистом хосте

`deploy/host_restore.py clean-plan <32-hex-id>` — отдельная **только читающая** проверка перенесённой пары `<id>.tar.gz` и `<id>.manifest.json` в закрытом `/var/lib/sovagrid-host-backups`. Обе копии должны принадлежать `root:root`, иметь режим `0600` и не быть symlink/hardlink; каталог — `root:root 0700`. Скрипт запускается от root из независимо проверенного исходного пакета SovaGrid, а не из ещё не проверенного архива. Схему исходников проверяющего пакета следует сверить с версией архива. Сам SHA-256 внутри пары обнаруживает повреждение, но не удостоверяет происхождение архива.

Режим заново сверяет хеш сжатого архива, каждый путь, тип, владельца и режим tar-записи, обязательные закрытые данные, встроенный `sovagrid-bundle.json` и SHA-256 всех исходников. Он не распаковывает файлы. Для Agent config/token проверяется одинаковый ненулевой числовой GID из архива; для локального Agent в Hub-only тот же GID требуется и у `hub-ca.pem`. Группа ещё не обязана существовать на чистом хосте. Затем только чтением проверяется, что пути управляемого состояния и пространства имён SovaGrid на целевом хосте отсутствуют; symlink либо групповой/общедоступный для записи родительский каталог отмечается отдельно. Каталог с самой перенесённой резервной копией исключён из проверки занятости. Дополнительно проверяются занятые UID/GID обязательных учётных записей, группа Web Agent и числовой GID Agent из самого архива через системный NSS; несовпадение даёт `TARGET_IDENTITY_CONFLICT` и закрывает `target_empty`. Результат содержит `verified`, `target_empty`, число конфликтов путей, число небезопасных путей, число конфликтов учётных записей и фиксированные коды блокировок без имён или содержимого секретных файлов. Изолированная фикстура проверила чистый временный root, занятый каталог, чужой GID Agent, неизвестный `sovagrid-*.service` и symlink родителя без распаковки.

После успешного `clean-plan` root может выполнить `deploy/host_restore.py stage <id>`. Команда повторно проверяет архив из того же открытого file descriptor, проверяет запас диска, создаёт закрытое дерево `/var/lib/.sovagrid-host-restore-staging/<id>` и атомарно публикует его после извлечения. Внутри дерева все файлы имеют `root:root 0600`, каталоги — `root:root 0700`, независимо от исходных владельцев и режимов; исходная метаинформация остаётся в архиве. Перед публикацией digest дерева сверяется с независимо вычисленным из проверенного архива ожидаемым digest, включая все созданные родительские каталоги; `stage-status` повторяет эту сверку. Это обнаруживает даже неверные байты, попавшие в дерево до первой записи квитанции. Распаковка не пишет в `/etc`, `/opt`, `/usr/local`, рабочие `/var/lib/sovagrid*`, не создаёт пользователей и не запускает службы. При отказе команда удаляет только своё временное дерево. `stage-status <id>` повторно проверяет исходный архив и содержимое закрытого дерева, включая посторонние или изменённые файлы; результат выдаёт только счётчики и фиксированные коды. Снимок стадии содержит закрытый `receipt.json` с digest дерева, SHA-256 архива и временем UTC. Стадия с тем же ID повторно не перезаписывается (`STAGE_EXISTS`); если процесс погиб до публикации, его закрытый временный каталог остаётся для ручного разбора root и не принимается за завершённую стадию.

`deploy/host_restore.py portable-clean-plan <32-hex-id>` добавляет к этой проверке переносимый экспорт: требует рядом с `images.tar` и `manifest.json` точный `receipt.json`, повторно сверяет оба архива, SHA-256 и платформы образов. Команда только читает Docker daemon, имена образов/контейнеров/сетей/томов, слушающие TCP-порты 80, 443, 8766 и 8767, UDP-порты управляемых WireGuard-инстансов из проверенного архива и доступное место. Порты извлекаются из ограниченного по размеру `state.json` и сверяются с `server.conf`; неоднозначное состояние VPN, включая внешнюю конфигурацию Amnezia, даёт `VPN_PORT_UNVERIFIED` и закрывает `target_empty`. Учитываются контейнеры как нового, так и старого формата Docker Compose. Команда сообщает счётчики конфликтов, совместимость архитектуры, `review_sha256` для точного подтверждения и коды блокировок без вывода сторонних имён. Отсутствующий Docker, несовместимая платформа, занятые ресурсы или недостаток места закрывают план. Проверка места закладывает запас на распаковку образов; перед будущим применением его придётся пересчитать. Основной `clean-plan` сохраняет прежнее поведение и блокер `DOCKER_IMAGES_NOT_INCLUDED`.

На чистом хосте root может выполнить `deploy/host_restore.py portable-stage <id> <review_sha256>` после просмотра переносимого плана. Команда отклоняет устаревший digest и любые блокеры кроме `APPLY_NOT_IMPLEMENTED`, повторно проверяет архив при создании закрытого дерева, затем сохраняет отдельную закрытую квитанцию, связывающую digest плана, SHA-256 архива, исходников, образов, точных `manifest.json` и `receipt.json` экспорта и дерева стадии. Метаданные экспорта читаются через закрытые file descriptor под общей блокировкой каталога и повторно сравниваются после полной проверки пары. `portable-stage-status <id>` заново проверяет дерево и переносимую пару, включая неизменность обоих файлов метаданных и хеши staged systemd unit, перечисленных в portable receipt; образы остаются в исходном закрытом каталоге, а не копируются второй раз. После прерывания между стадией архива и квитанцией тот же запрос можно безопасно повторить. Ни одна из команд не импортирует Docker-образы и не пишет в рабочие пути.

`deploy/host_restore.py portable-apply-preview <id>` повторно проверяет готовую стадию и состояние чистого хоста, возвращая `apply_review_sha256`, число конфликтов, список ранее активных управляемых unit и `target_ready`. Digest связывает текущий план цели с точными хешами стадии, архива, Docker tar и двух файлов метаданных экспорта. Изменение цели, архива, квитанции или unit-файлов даёт новый digest либо отказ. Квитанция v1 остаётся пригодной для `verify-portable`, `portable-clean-plan`, `portable-stage` и проверки стадии, но в новых исходниках предпросмотр полного применения добавляет для неё блокер `RECEIPT_V1_UNSUPPORTED` и не выставляет `target_ready`: у v1 нет состояний включения всех unit. Этот digest пока не принимает никакая команда применения: `apply_available:false` и `APPLY_NOT_IMPLEMENTED` остаются в ответе и для v2. Проверка может занять время, потому что повторно читает оба архива и дерево стадии.

`apply_available` всегда `false`: **команды установки в рабочие пути нет**. Даже `target_empty:true`, успешный `stage-status` и проверенная переносимая пара не гарантируют рабочую сеть и будущий старт служб; архив не является образом Ubuntu. Проверка пустоты целевого хоста — снимок состояния, который может устареть сразу после ответа. Для полноценного восстановления ещё нужны транзакция с блокировкой записывающих служб, выделение UID/GID из архива, безопасный импорт и закрепление экспортированных образов, установка с записью каждого шага в durable journal, проверка здоровья и журналируемый откат. Docker `load` может оставить слои и теги даже после неуспеха; предварительная чистота имён ещё не даёт безопасной операции отката. `stage` не является восстановлением, поэтому не останавливает службы и не меняет рабочую установку.

Будущий `apply` должен вернуть закрытый каталог Web Agent и журнал заданий до запуска его службы, сверить SHA-256 каждого versioned bundle, затем установить marker и оба systemd unit. Группу сокета `sovagrid-web-agent` с GID `10005` нужно создать до активации socket; socket и service должны быть готовы до запуска Hub/Web с bind mount сокета. Начинать удалённые установки из сохранённого журнала можно только после восстановления локального Hub и проверки прежнего SSH host key. Текущие `clean-plan`, `stage` и `stage-status` лишь проверяют и подготавливают данные; такой порядок ещё не реализован как команда восстановления.

### Контракт следующей транзакции восстановления

Этот раздел описывает контракт `portable-apply`, который должен пройти проверку до включения публичной команды. Исполнитель принимает только `<id>` и `apply_review_sha256` из `portable-apply-preview`, берёт exclusive lock закрытого каталога стадий и повторяет все проверки уже под lock. Для отсутствия гонки с другой установкой каждая публикация в рабочий путь использует `renameat2(RENAME_NOREPLACE)` относительно проверенного file descriptor родительского каталога и повторную проверку того, что источник всё ещё совпадает со стадией. Пути из архива нельзя передавать в shell или копировать рекурсивно по непроверенному пути.

Публикуемые ресурсы ограничены проверенными архивными записями под `/etc/sovagrid*`, `/var/lib/sovagrid*`, `/opt/sovagrid-*` и точными leaf-файлами `sovagrid-*` в `/etc/systemd/system`, `70-sovagrid-vpn-routing.conf` в `/etc/sysctl.d`, `sovagrid-vpn-ctl` в `/usr/local/bin` и `sovagrid-vpn-broker` в `/usr/local/libexec`. Каталоги перед публикацией должны находиться в закрытых shadow-каталогах **на той же файловой системе, что их адресат**. Метаданные владельца, группы и режима восстанавливаются из повторно проверенного tar, байты — из стадии, чей digest уже независимо вычислен из tar. Любой другой существующий SovaGrid-путь, symlink или опасный родитель блокирует команду. Создаваемые родительские каталоги тоже входят в журнал и удаляются при откате только если они пусты и принадлежат этой операции.

До первого изменения исполнитель должен синхронно записать закрытый журнал с ID, обоими CAS, точными SHA-256 всех пяти входных файлов, layout, manifest ресурсов и снимком отсутствующих имён Docker/путей/NSS. Каждая следующая запись состояния выполняется через отдельный `0600` temporary, `fsync(file)`, атомарный rename и `fsync(directory)`; перед каждой внешней операцией сохраняется её intent. Предлагаемые фазы: `prepared` → `identities_reserved` → `images_loaded` → `files_switched` → `services_started` → `healthy` → `committed`. При отказе или повторном запуске `recover` сверяет точные inode/хеши созданных файлов, числовые UID/GID, Docker tag→image ID и управляемые unit, затем откатывает в обратном порядке. Если ресурс отличается от ожидаемого после вмешательства другого процесса, `recover` оставляет журнал в `recovery_required` и ничего чужого не удаляет. Прерванный `prepared` удаляет только закрытые shadow-каталоги; успешный `committed` не запускается повторно.

Импорт `images.tar` должен читать уже открытый проверенный FD, удерживать lock входной пары, после `docker image load` проверить каждый тег `sovagrid-<service>:local` по **экспортированному config digest** (`exported_configs`), `RootFS.Layers`, платформе и точному составу сервисов. Исходный Docker image ID в квитанции может отличаться от экспортированного config digest при OCI-конвертации, поэтому его нельзя слепо сравнивать с новым daemon ID. Откат снимает только теги, совпадающие с записанными экспортированными digest; неиспользуемые слои Docker может оставить до отдельной очистки. `systemctl daemon-reload`, включение и старт unit, `docker compose up -d --no-build` и health-check Hub/Web/Gateway выполняются только после публикации всех файлов и закрытого журнала; Web Agent socket поднимается до Hub/Web. Любая ошибка здоровья запускает откат, а не выдаёт `complete`.

В исходниках после `server-v0.14.1` два ранее отсутствовавших входных условия подготовлены, но **не включают применение архива**. Квитанция v2 записывает `active`, `enablement` и SHA-256 каждого присутствующего управляемого unit; v1 по-прежнему проверяется и стадируется, но не считается готовой для полного применения. Отдельный режим `run.sh --restore-dependencies-only --expected-source-manifest-sha256 <sha256>` принимает только проверенный пакет исходников в закрытом root-owned каталоге под `/root` на пустом Ubuntu 22.04/24.04/26.04 с systemd. До установки пакетов он сверяет точный SHA-256 манифеста и чистоту цели; если Python уже доступен, также проверяет всё дерево исходников. Затем режим устанавливает недостающие Python, Docker/Compose и `iproute2` из настроенных Ubuntu-репозиториев и повторно сверяет дерево и чистоту цели. Если Python изначально отсутствует, код из проверяемого дерева до итоговой проверки не исполняется. Режим не создаёт учётных записей, секретов, unit-файлов, контейнеров или рабочего дерева SovaGrid. Он ещё не проверен на одноразовой Ubuntu VM и не входит в стабильный архив; не используйте его как команду восстановления. Для безопасного `portable-apply` всё ещё требуются разработка транзакции с долговечным журналом, восстановлением после прерывания и откатом, а также проверки аварийного завершения после **каждой** фазы на одноразовом Ubuntu-хосте. Локальные тесты стадии покрывают порчу staged-байтов до первой квитанции, подмену receipt/manifest экспорта, изменение хеша systemd unit и устаревший CAS цели.

Перед реализацией применения остаются конкретные требования к контракту:

- Общая ранняя блокировка установки должна охватывать обычный `run.sh`, подготовку зависимостей и восстановление до создания пользователей и данных. Порядок блокировок: installation, staging, image-export. Нельзя удерживать exclusive lock стадии и повторно вызывать нынешний `stage_status()` через новый shared FD; внутренней проверке нужен уже удерживаемый descriptor.
- Неявные родители в закрытой стадии имеют режим `0700` и не представляют метаданные живых каталогов. Применение должно выводить точные режимы и владельцев родителей из закрытого контракта установщика, создавать пустые runtime-каталоги Agent/терминала и журналировать их. Пользователь Agent получает новый ненулевой системный UID с архивным первичным GID; повторное использование NSS-записей требует проверки home, shell и дополнительных групп.
- До публикации файлов следует проверить зависимости архивных функций: WireGuard требует `wireguard-tools` и `python3-cryptography`, маршрутизация — `nftables`. Команды Docker должны использовать локальный socket. Входные архивы, метаданные и locks удерживаются открытыми на протяжении всей транзакции.
- Первый вариант полного применения следует ограничить схемой `full`, квитанцией v2 и состояниями автозапуска `enabled`, `disabled`, `static`. Другие состояния и Hub-only получают явные блокеры. Восстановленный публичный адрес обязан пройти проверку локального интерфейса цели до мутаций; HTTPS-ответ прежнего сервера не подтверждает здоровье нового. Перенос на другой IP потребует отдельного подтверждённого override, включённого в CAS.

### Исполнитель в новых исходниках — публичное применение ещё выключено

Проверка образов учитывает различия классического Docker и containerd: ID образа может обозначать конфигурацию, manifest или index. Исполнитель связывает допустимые ID с проверенным содержимым архива. Если Docker преобразовал формат при загрузке, повторный ограниченный экспорт должен подтвердить тот же digest конфигурации, RootFS и платформу. Compose получает проверенный ID, который действительно поддерживает целевой daemon. Публичные манифест и квитанция при этом не меняются.

План заранее учитывает дополнительные 8 ГиБ свободного места для временной проверки образов сверх места самой копии и восстановления. Это запас, а не заранее записываемый файл размером 8 ГиБ. Временный архив ограничен по размеру и времени, не имеет опубликованного имени и удаляется при закрытии процесса. Для небольшой установки рекомендуется цель с диском от 20 ГиБ; решающими остаются значения «свободно» и «требуется» в плане конкретной копии.

После `server-v0.14.1` добавлены внутренние модули `portable_restore_apply.py`, `portable_restore_shadow.py`, `portable_restore_compose.py`, `portable_restore_runtime.py` и `portable_restore_queue.py`. Они связывают все пять входных файлов через удерживаемые FD, порядок locks `installation → staging → image-export`, закрытый план ресурсов и долговечный журнал. Каждая внешняя операция получает записанный и синхронизированный intent; прерванная установка восстанавливается обратными действиями, а не повторным запуском команд. Отдельные root-only команды `portable-apply-status <id>` и `portable-apply-recover <id>` читают журнал и восстанавливают принадлежащие ему ресурсы. `portable-apply <id> <apply_review_sha256>` сохраняет отказ `APPLY_NOT_IMPLEMENTED`, пока `APPLY_ENABLED=False`; ответы существующих предпросмотров по-прежнему имеют `apply_available:false`.

Для мастера переноса добавлен отдельный [протокол целевого сервера](deploy/PORTABLE_RESTORE_TARGET.md). Проверенный исполнитель доставляется независимо от копии в закрытый каталог под `/root`, автоматически готовит зависимости и принимает пять файлов по одному SSH-соединению. Незавершённая передача продолжает только совпадающий фрагмент; регистрация проверяет архив, Docker-слои и квитанцию до публикации входных имён. Подготовленный `start` запускает независимую systemd-операцию; повтор после потерянного ответа сначала читает статус. Явный `retry` после полного отката сохраняет прежние журнал/план/Compose по inode и хешам, получает новый nonce и требует нового подтверждения; прерванное архивирование можно продолжить после переподключения. Поддержка исполнителя, физическая готовность цели и блокеры разделены в общем контракте. Пользовательские мастера ещё собираются; производственное применение остаётся выключенным.

Сначала синхронизируется журнал, затем атомарно публикуется постоянный файл `/var/lib/.sovagrid-host-restore-in-progress`, привязанный к ID и digest подтверждения/ресурсов. Обычная установка и bootstrap отказывают при его наличии после получения общего installation lock. Fence остаётся после смерти процесса и перезагрузки; он снимается только после синхронизированного `committed` или полного `rolled_back`. Повторное восстановление конечной операции убирает только её собственный совпадающий fence. Новая операция дополнительно проверяет остальные журналы стадий и отказывает при незавершённом восстановлении, даже если fence был удалён вручную.

План выводит владельцев и режимы из проверенного tar. Неявные живые родители `/etc/sovagrid` и `/var/lib/sovagrid`, пустые рабочие каталоги Agent/терминала, обязательные закрытые рабочие каталоги backup-брокера и нужные каталоги Unix-сокетов имеют отдельные правила; закрытые режимы стадии в них не копируются. Agent получает свободный ненулевой системный UID и архивный GID. Существующие NSS-записи не усыновляются. Shadow-деревья создаются только после intent, на файловой системе адресата, с закрытым nonce-маркером владения. После прерывания частично записанный файл удаляется только при совпадении с префиксом проверенного исходника; неизвестные пути или изменённые байты сохраняются.

Docker получает только удерживаемый проверенный `images.tar` через явный локальный socket. После импорта сверяются экспортированный config digest, RootFS и платформа каждого сервиса. Compose запускается с `--no-build --pull never`; отдельный закрытый overlay помечает контейнеры и сеть ID восстановления и digest подтверждения. Перед остановкой/удалением исполнитель проверяет весь состав, image/config hash и метки, а также отсутствие чужих сетевых endpoints. `compose down`, `prune`, принудительное удаление и сторонние Docker-ресурсы не используются. Сокеты и ранее активные связанные broker services запускаются до Hub/Gateway, Agent — после Compose, таймеры — последними. Здоровье проверяется через локальный HTTP, сохранённый CA для `https://localhost:8767`, контракт SSH Gateway и Agent/systemd. Публичный TLS проверяется соединением с локальным портом 443 и именем настроенного адреса, поэтому прежний сервер не может подтвердить новый.

Данные Hub, Caddy и runtime-инвентарей могут законно измениться сразу после старта. Эти изменения не считаются ошибкой успешного запуска. При последующей ошибке здоровья автоматический откат **не удаляет изменившиеся данные**: он останавливается в `recovery_required` и сохраняет fence для разбора root. Это отдельный предел автоматического восстановления, а не успешный полный откат. Активная либо включённая в автозапуск VPN-маршрутизация, перенос на другой публичный IP, публичный staging ACME и неподдерживаемые systemd enablement states пока отказывают до мутаций; перенос активного WireGuard/Amnezia и изменяемой конфигурации Docker требует отдельных адаптеров.

Локальные проверки покрывают смерть процесса у каждой записи журнала, partial shadow/owner, замену одинаковыми байтами на чужом inode, изменения родителя, NSS-пароля/групп, образа/RootFS, Compose-меток и сети, очистку своего fence и сохранение чужого состояния. Они не заменяют Ubuntu-проверку. Подготовлен `tests/portable_restore_apply_vm.py`: только root на явно выбранной одноразовой GitHub-hosted Ubuntu, после общего теста подписанного обновления. Он создаёт три переносимые копии настоящим orchestrator, сохраняет все входные файлы и проверенный код отдельно под `/root`, удаляет только доказанное состояние данной CI-установки и проверяет смерть процесса перед первым стартом службы с восстановлением, настоящий запуск Hub/Agent/Web/команд/файлов/PTY и отказ здоровья после записи в SQLite с обязательным сохранением данных/fence. Последний сценарий намеренно оставляет одноразовую VM в `recovery_required`; после него не запускаются другие проверки backend. До успешного выполнения и разбора этого gate публичное применение не включается.


Дополнительные проверки нового исполнителя закрывают два пути неявного запуска. До мутаций проверяются полные, префиксные и общие для типа unit drop-in каталоги во всех стандартных системных путях systemd. После daemon-reload и перед действиями `DropInPaths` обязан быть пустым, а `FragmentPath` — точным восстановленным файлом. Проверяется полный граф `.wants`, `.requires` и `.upholds`, включая ссылки из другого target и стандартных `/run`/vendor путей; чужие пути активации сохраняются и блокируют восстановление. Перед commit повторно сверяются состояния всех восстановленных unit, включая неактивные.

Перед первой активацией отдельно журналируется карантин команд Hub. Новый адаптер `portable_restore_queue.py` создаёт частную копию SQLite, учитывает WAL, под UID/GID Hub отменяет все `queued` задания и очищает текст команды, удаляет ожидающие подтверждения Telegram и записывает только количества в аудит. Исходные DB/WAL/SHM сохраняются вне рабочего дерева до commit; обратная операция может вернуть только точно совпадающие исходные inode и производную базу. Законные записи после запуска нельзя отменить обратным SQL: при несовпадении данных сохраняются база и fence для ручного восстановления. Карантин и его аварийные границы ещё требуют проверки на одноразовой Ubuntu. Конфигурации VPN не означают включение туннеля: активная либо включённая в автозапуск маршрутизация пока получает явный блокер, а WireGuard/Amnezia требуют отдельного подтверждённого включения.

Разрушительный VM gate теперь требует `GITHUB_RUN_ID` и независимый `SOVAGRID_RESTORE_EXPECTED_MANIFEST`, вычисленный из проверяемого артефакта, до копирования исходников. Сразу после первоначальной установки отдельный `record-fixture` создаёт root-private реестр `/var/lib/.sovagrid-portable-restore-ci-fixture.json`. Он привязывает установку к запуску CI, закрытому списку дочерних путей и inode/байтам созданных объектов. Производители тестовых гостевых машин, возвращённого Web-задания, подписанного кандидата и снимков регистрируют свои точные ID; очистка не усыновляет свежий рекурсивный обход. Перед выключением каждого гостя сверяются rootfs, machine-id, unit, argv/start-time процесса nspawn и корень/PID лидера. Независимая копия под `/root` исключает `__pycache__`, повторно сверяет все исходники с известным pin и отказывает при bytecode. Неизвестный потомок под данными или кандидатами, изменённая NSS-запись либо другой гость останавливают очистку до её первого действия.

Первый снимок VM остаётся без ожидающих команд для проверки полного возврата после смерти процесса. Перед вторым и третьим в исходной базе сохраняются задание с действующей сессией и закрытым разрешением команд, а также ожидающее подтверждение Telegram. После восстановления gate требует отменённое задание с пустым текстом, удалённое подтверждение и агрегированный аудит; после настоящего включения команд/PTY/файлов контрольный файл старой команды обязан отсутствовать. Все тестовые подключения к SQLite выполняются под UID/GID Hub без дополнительных групп. Этот сценарий подготовлен, но ещё не выполнялся в Ubuntu CI; `APPLY_ENABLED` остаётся `False`.
